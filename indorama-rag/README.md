# Indorama LMS — ผู้ช่วยตอบเรื่องระบบ (RAG)

ตอบคำถามเชิงระบบเกี่ยวกับ LMS เดิมของ Indorama จาก schema, routing table และ
โครงสร้างซอร์สโค้ดที่อยู่ในไฟล์ export

**แยกจาก kai-proctor โดยสิ้นเชิง** ใช้ repo เดียวกันเพื่อความสะดวก แต่ไม่มี import
ข้ามกัน ไม่แชร์ฐานข้อมูล และ deploy แยกกันได้

```bash
python -m ingest.build /path/to/export_20260804_065758.zip
```

```bash
RAG_INDEX_PATH=index.sqlite uvicorn app.main:app --port 8100
```

## Deploy

สแตกของตัวเอง ไม่ใช่ service ที่แทรกอยู่ใน `docker-compose.yml` ของ kai-proctor —
ไม่แชร์ฐานข้อมูล ไม่แชร์การตั้งค่าโมเดล ไม่แชร์วงจรชีวิต การเอาไปรวมจะทำให้เครื่องมือ
ภายในของลูกค้าผูกกับรอบปล่อยของผลิตภัณฑ์คนละกลุ่ม และต้องดับผู้ช่วยเพื่อรีสตาร์ท Moodle

```bash
RAG_EXPORT=/path/to/export.zip docker compose run --rm build-index
```

```bash
docker compose up -d rag
```

**ดัชนีไม่ถูกใส่ไว้ใน image** เพราะมันเป็น build artefact ของ export ชุดหนึ่ง (build report
บันทึก SHA-256 ของชุดนั้นไว้) และชุดที่ใช้อยู่ยังมีข้อมูลส่วนบุคคลที่ขอให้ลูกค้าลบ —
การอบมันลงไปใน layer จะทำให้มันไปอยู่ในทุก registry ที่ push image ไป และ layer อยู่นาน
กว่าการตัดสินใจลบไฟล์ จึง mount เข้าไปแทน และ mount แบบ **read-only** เพราะบริการไม่เคย
เขียนดัชนี — บั๊กจึงเปลี่ยนสิ่งที่คำตอบสร้างมาจากไม่ได้

| ตัวแปร | ค่าตั้งต้น |
|---|---|
| `RAG_LLM_BASE_URL` | `http://host.docker.internal:11434/v1` (Ollama บนเครื่อง host) |
| `RAG_LLM_MODEL` | `qwen2.5:7b-instruct` — วัดแล้ว ดู [reports/MODEL-COMPARISON.md](reports/MODEL-COMPARISON.md) |
| `RAG_INDEX_DIR` | `./index` |
| `RAG_PORT` | `9200` |
| `RAG_CONTEXT_CHUNKS` | `4` |

## Agent — คุยต่อเนื่อง เรียกเครื่องมือเอง เก็บประวัติเป็น .md

```bash
curl -s localhost:8100/chat -H 'content-type: application/json'   -d '{"user_id":"alice","message":"tbl_company มีคอลัมน์อะไรบ้าง"}'
```

ตอบกลับมาพร้อม `conversation_id` ส่งกลับไปในคำถามถัดไปเพื่อคุยต่อ

| endpoint | ทำอะไร |
|---|---|
| `POST /chat` | หนึ่งเทิร์น เริ่มบทสนทนาใหม่ถ้าไม่ส่ง `conversation_id` |
| `GET /conversations?user_id=` | รายการบทสนทนา + พื้นที่ที่ใช้ |
| `GET /conversations/{id}?user_id=&raw=true` | ดึงไฟล์ `.md` ดิบไปเลย |
| `PATCH /conversations/{id}` | เปลี่ยนชื่อ |
| `DELETE /conversations/{id}?user_id=` | ลบบทเดียว |
| `DELETE /conversations?user_id=&confirm=` | ลบทั้งหมด (ต้องยืนยันด้วย user_id ซ้ำ) |

**`/ask` เดิมยังอยู่ ไม่ได้ถูกแทนที่** มันคือคำถามเดียว retrieval เดียว ไม่มีดุลพินิจของ
โมเดลว่าจะดูอะไร — จึงเป็นเครื่องมือที่ใช้ตอบว่า "คำตอบผิดเพราะ retrieval หรือเพราะ agent loop"

### เครื่องมือที่ agent เรียกได้ ([`app/tools.py`](app/tools.py))

`get_table` · `search` · `get_source_file` · `list_sensitive_tables` ·
`list_tables` · `list_routes` · `get_relationships`

ทั้งหมดอ่านจากดัชนี ไม่มีตัวไหนแตะไฟล์ export เครือข่าย หรือ filesystem —
**ชุดนี้คือขอบเขตของ agent ทั้งหมด** และสั้นพอจะอ่านจบในหนึ่งนาที

**ไม่มี `run_query` ที่รับ SQL** ซึ่งจะเหลือเครื่องมือเดียวแทนเจ็ดตัว และจะเป็นการยื่น
ภาษาคิวรีที่จ่อไปที่ดัชนีให้โมเดล — หลักประกันทุกข้อว่าคำตอบสร้างจากอะไร จะกลายเป็น
ขึ้นกับสิ่งที่มันพิมพ์ `list_sensitive_tables` คืนชุดผิดไม่ได้ แต่ SELECT ทำได้

### ประวัติแชท ([`app/memory.py`](app/memory.py))

ไฟล์ `.md` หนึ่งไฟล์ต่อบทสนทนา ในโฟลเดอร์ของแต่ละ user + ดัชนี SQLite เก็บ metadata

การแยกนี้ไม่ใช่ความซ้ำซ้อน: การไล่รายการบทสนทนาหรือรวมพื้นที่ที่ใช้ ต้องทำได้โดยไม่เปิด
และ parse ทุกไฟล์ — แต่**ไฟล์คือสิ่งที่สัญญาไว้ ไฟล์จึงเป็นสำเนาที่ต้องรอด** ดัชนีหายสร้างใหม่
จากโฟลเดอร์ได้ ไฟล์หายไม่มีอะไรเอากลับมาได้

ขอบเขตของเทิร์นเป็น HTML comment ซึ่ง Markdown แสดงผลเป็นความว่างเปล่า และตัว parser
ทนกับสิ่งที่คนแก้ไฟล์เองใส่เข้าไป — **มีเทสต์ว่าแก้ไฟล์ด้วยมือแล้วยังอ่านกลับได้**

โควตา 1GB ต่อ user ตามที่กำหนด — เกินแล้ว**ปฏิเสธพร้อมรหัส ไม่ตัดข้อความเงียบๆ**
เพราะบทสนทนาที่หยุดบันทึกเงียบๆ หน้าตาเหมือนบทสนทนาที่ไม่มีใครคุยต่อ

## ตอบอะไรได้ ตอบอะไรไม่ได้

| ถามได้ | ตัวอย่าง |
|---|---|
| โครงสร้างตาราง | "tbl_contentEnroll มีคอลัมน์อะไร ผูกกับตารางไหน" |
| ข้อมูลอ่อนไหว | "ตารางไหนเก็บข้อมูลส่วนบุคคลบ้าง" |
| Route / API | "route ของ Channels มีอะไรบ้าง" |
| ซอร์สโค้ด | "Authorization_Token.php ทำอะไร" |

**ตอบไม่ได้ และไม่ควรถาม** อะไรก็ตามที่เกี่ยวกับ*เนื้อหา*ในระบบ — มีผู้เรียนกี่คน
คอร์สนี้สอนอะไร ใครลงทะเบียนบ้าง ดัชนีนี้ไม่เคยเห็นข้อมูลสักแถวเดียว

เหตุผลอยู่ที่ไฟล์ export เอง: จาก 6.05 ล้านตัวอักษรที่เป็นข้อความอิสระ ~85% เป็น log
ส่วนเนื้อหาหลักสูตรจริงมี ~400 KB และเกือบทั้งหมดเป็นชื่อเรื่องเปล่า — คอร์ส 16,431
รายการไม่มีคำอธิบายสักรายการ และ `tbl_contentLang` 1,880 รายการมีคำอธิบายจริง 62 รายการ
ตัวบทเรียน (วิดีโอ, SCORM, เอกสาร) ไม่ได้ export มา

## ข้อมูลส่วนบุคคล — หลักประกันอยู่ที่โครงสร้าง ไม่ใช่ที่ตัวกรอง

ไฟล์ export ประกาศตัวเองว่า `"anonymized": true` **ซึ่งไม่จริง** — มีอีเมลจริงของ
พนักงาน 864 รายการ (สแกนเฉพาะไฟล์ที่เล็กกว่า 40MB) โดเมน `indorama.net` และ
โดเมนย่อยรายประเทศ กระจุกที่ `tbl_lg` (781), `ci_sessions` (149)

ดัชนีนี้ไม่มีอีเมลแม้แต่รายการเดียว และเหตุผล**ไม่ใช่**เพราะกรองออก แต่เพราะ
**ส่วนที่มีข้อมูลแถวเปิดอ่านไม่ได้เลย**

`GuardedArchive` อนุญาตให้อ่านได้แค่ 5 ส่วน — `manifest.json`, `schema/`,
`dictionary/`, `api/`, `source_code/` — ขออ่าน `learning/`, `master/`,
`activities/`, `integrations/`, `assessments/` แล้ว **โยน `SectionRefused`**
ตรวจสอบได้ด้วยการอ่านโค้ด 20 บรรทัด ไม่ต้องไปไล่ดูว่า regex บังเอิญจับอะไรได้บ้าง

ตัวกรอง regex (อีเมล/IP/JWT) ยังทำงานอยู่ในฐานะ**ตาข่ายรอง** บน chunk ทุกชิ้น
บน export ชุดนี้มันจับได้ 0 รายการ ซึ่งเป็นผลที่ถูกต้อง ไม่ใช่สัญญาณว่าพัง

### สิ่งที่หลุดผ่านทุกด่าน และวิธีที่เจอ

`tbl_company.default_user_password` มี `DEFAULT ('Indorama2025')` — **รหัสผ่านตั้งต้น
จริงของทุกบัญชีที่ลูกค้าสร้าง** ทุกกลไกข้างบนเล็งไปที่ *ข้อมูลแถว* แต่ DEFAULT
constraint เป็นส่วนหนึ่งของ*นิยามคอลัมน์* มันจึงเดินผ่านทุกด่านมาพร้อมกับโครงสร้าง

เจอโดยการเปิดอ่าน chunk ที่สร้างเสร็จแล้ว ไม่ได้เจอด้วยการตรวจใดๆ

ตอนนี้ค่า DEFAULT ที่เป็น string literal บนคอลัมน์ที่จัดชั้น `sensitive` ถูกปกปิด
ส่วนค่าที่เป็นตัวเลข (`((1))`) ยังคงไว้ — มันบอกพฤติกรรมตั้งต้นของระบบและไม่เปิดเผยอะไร
มีเทสต์ `test_the_default_password_does_not_reach_the_index` กันการถอยหลัง

> **ยังต้องส่งหนังสือแจ้งลูกค้าอยู่ดี** ดัชนีสะอาดไม่ได้แปลว่าไฟล์ต้นทางหายไป —
> ไฟล์ยังอยู่ในมือเรา ดูร่างที่ `../docs/drafts/`

## ทำไมไม่ใช้ embedding

คำถามที่ระบบนี้จะเจอ**ระบุชื่อสิ่งที่ถามแบบเป๊ะๆ** — `tbl_contentEnroll`,
`Authorization_Token`, `routes.php` — ส่วน dense embedding ถูกออกแบบมาให้คำที่
*ต่างกัน*แต่ความหมายใกล้กันอยู่ใกล้กันในเวกเตอร์สเปซ ซึ่งตรงข้ามกับที่ identifier ต้องการ
มันจะกลืน `tbl_content` / `tbl_contentLang` / `tbl_contentEnroll` เข้าหากัน แล้วตอบชื่อ
ตารางผิดด้วยน้ำเสียงมั่นใจเท่าตอบถูก

คลังข้อมูลก็แค่ 251 KB — vector store จะเป็นภาระ (บริการที่ต้องรัน โมเดลที่ต้องตรึง
มิติที่ต้อง migrate) ที่ซื้อมาแก้ปัญหา recall ที่คลังนี้ไม่มี

ใช้ SQLite FTS5 แทน โดยเลื่อน `_` ให้เป็นตัวอักษรใน `unicode61` ไม่งั้น
`tbl_content_skills` จะถูกหั่นเป็นสามชิ้นที่แมตช์กันเองมั่วไปหมด

### ในดัชนีไม่มีภาษาไทยเลย

เวอร์ชันแรกทำ **character trigram** ของภาษาไทยควบคู่ไปด้วย ด้วยเหตุผลว่าไทยไม่มีช่องว่าง
จึงต้องมี tokenisation ของตัวเอง — แต่พอ**นับดูจริงว่าในคลังมีภาษาไทยอะไรบ้าง** ก็พบว่ามี
**28 รูปแบบ และทุกอันคือ label ที่โค้ดนี้เขียนเอง** ไม่มีภาษาไทยจาก export แม้แต่คำเดียว
(คลังคือ schema, route และ PHP identifier)

แปลว่า trigram กำลังแมตช์ scaffolding ของตัวเอง มันได้ผลโดยบังเอิญกับ "ข้อมูลอ่อนไหว"
เพราะ label หนึ่งบังเอิญมีคำนั้น และมันพังแบบที่ความบังเอิญพัง — *"วันนี้อากาศเป็นยังไง"*
ได้ตารางกลับมาสามตัว เพราะคำเชื่อมภาษาไทยสร้าง trigram ที่ชนกับคำเชื่อมใน label

ตอนนี้ภาษาไทยเข้าถึงดัชนีผ่าน [`app/lexicon.py`](app/lexicon.py) ซึ่งเป็น**คำศัพท์ควบคุม**
แต่ละคำถูก map ไปยัง anchor ภาษาอังกฤษและชนิด chunk ที่มันหมายถึง — คำถามภาษาไทยจึงไป
ค้นภาษาอังกฤษที่คลังทำมาจากมันจริงๆ

รายการสั้นเพราะโดเมนเล็ก และตั้งใจให้อ่านและเถียงได้ **คำที่หายไปจากรายการ = คำถามที่จะถูก
ปฏิเสธ** ซึ่งเป็นความล้มเหลวที่มองเห็นและร้องเรียนได้ ไม่ใช่ความล้มเหลวเงียบๆ ที่คืนคำตอบ
มั่นใจเกี่ยวกับอะไรก็ไม่รู้

### ชื่อที่ตรงเป๊ะชนะการจัดอันดับ ไม่ใช่ถ่วงน้ำหนักสู้กัน

ถาม *"โครงสร้างของ tbl_certificate"* แล้วเคยได้ `tbl_lg` มาเป็นอันดับหนึ่ง เพราะร้อยแก้ว
ชนะ identifier ในการจัดอันดับ — ไม่มีน้ำหนักชุดไหนแก้ได้อย่างซื่อสัตย์ จึงแยกสองสัญญาณ
แทนการถ่วงให้สมดุล: ถ้าคำถามเอ่ยชื่อที่ตรงกับ `ref` ของ chunk ถือว่าคำถาม**ชี้คำตอบของ
ตัวเองแล้ว** ตอบก่อนโดยไม่ปรึกษาการจัดอันดับ

คำในโดเมนค้นแบบ prefix (`controller*` เจอ `controllers` — `unicode61` ไม่มี stemming)
ส่วน identifier ค้นแบบตรงเป๊ะ เพราะ `tbl_content*` จะไปโดน `tbl_contentLang` และ
`tbl_contentEnroll` ซึ่งคือความสับสนที่ดัชนีนี้มีไว้เพื่อหลีกเลี่ยง

## อยู่ในเรื่อง — สี่ชั้น บังคับในโค้ด ไม่ใช่ขอไว้ใน prompt

แต่ละชั้นมีอยู่เพราะชั้นก่อนหน้าถูกวัดแล้วพบว่ารั่ว

### ชั้น 1 — นอกเรื่องไม่ถึงโมเดล ([`app/scope.py`](app/scope.py))

ตัดสิน**ก่อน**ค้นและก่อนเรียกโมเดล คำถามอยู่ในขอบเขตเมื่อมีอย่างน้อยหนึ่งอย่าง:
ชื่อที่คลังมีจริง · คำโดเมนภาษาอังกฤษ · คำในพจนานุกรมไทย — **ไม่มีอย่างอื่นนับ**
โดยเฉพาะ "ข้อความไปตรงกับใน chunk" ไม่นับ เพราะคลังมีคอลัมน์ชื่อ `data`, `name`,
`type`, `status` และกฎที่ใจกว้างพอจะรับคำพวกนี้ก็รับเกือบทุกประโยคในทั้งสองภาษา

| | ผลวัดกับ export จริง |
|---|---|
| คำถามนอกเรื่อง 10 ข้อ | **ปฏิเสธ 10/10** (`off_topic`, ไม่เรียกโมเดล) |
| คำถามในเรื่อง 12 ข้อ | **หา chunk เจอ 12/12** |

ก่อนมีชั้นนี้ คำถามนอกเรื่องภาษาไทย **5 จาก 6 ข้อได้ material กลับมา** และเมื่อ material
กลับมาแล้ว บริการไม่เหลืออะไรให้ปฏิเสธ — โมเดลได้นิยามตารางสามตัวกับคำถามเรื่องอากาศ
แล้วมันก็ตอบ

`off_topic` กับ `no_material` แยกกันเพราะความหมายต่างกันสำหรับคนอ่าน: อันหนึ่งบอกว่า
ถามผิดที่ อีกอันบอกว่าถามถูกที่แต่คลังไม่ลึกถึงขนาดนั้น

### ชั้น 2 — ตอบได้เฉพาะสิ่งที่ถูกวางให้ดู

ตรวจกับ chunk ที่ retrieve มาสำหรับคำถามนั้น **ไม่ใช่ทั้งคลัง 519 chunk** การถามว่า
"ชื่อนี้มีอยู่ในระบบไหม" ตอบคนละคำถามกับ "ชื่อนี้อยู่ใน material ที่คุณได้รับหรือเปล่า" —
ชื่อตารางจริงที่โมเดลไม่เคยเห็นในรอบนี้ ไม่ได้มาจาก material แต่มาจากที่อื่น
ซึ่ง "ที่อื่น" คือสิ่งเดียวที่ผู้ช่วยนี้ห้ามใช้

### ชั้น 3 — ชื่อ snake_case ต้องมีอยู่ใน material

เดิมตรวจแค่ `tbl_*`/`ci_*` และ path `.php` โดยจงใจไม่ตรวจชื่อคอลัมน์ เพราะชนกับคำธรรมดา

**การทดสอบกับโมเดลจริงหักล้างข้อยกเว้นนั้น** ถาม qwen2.5:7b-instruct ว่า `tbl_company` มีคอลัมน์อะไร
มันตอบ `com_default_user_password` — ชื่อจริงคือ `default_user_password` และมันเติม `com_`
เพราะคอลัมน์อื่นทุกตัวในตารางนั้นขึ้นต้นแบบนั้น **การประกอบชื่อจากรูปแบบของเพื่อนบ้าน
คือสิ่งที่ language model ถูกสร้างมาให้ทำ** จึงเป็นการแต่งที่เป็นระบบ ไม่ใช่พลาดนานๆ ครั้ง

ข้อโต้แย้งเดิมใช้ได้กับคำเดี่ยว แต่ใช้ไม่ได้กับรูปทรงนี้ — **ขีดล่างกลางคำไม่มีในร้อยแก้ว
ไทยหรืออังกฤษ** false positive ที่ข้อยกเว้นนั้นปกป้องอยู่จึงไม่เกิด

คอลัมน์คำเดียว (`id`, `status`, `ordering`) ยังไม่ถูกตรวจ — ยอมรับเศษนี้อย่างรู้ตัว เพราะ
แยกจากคำภาษาอังกฤษไม่ได้ และตัวตรวจที่ปฏิเสธคำตอบที่ถูกคือตัวตรวจที่จะถูกปิดทิ้ง

นอกจากนี้ยังตรวจ **ชื่อแบบเต็ม `tbl_x.col`** กับ chunk ของตารางนั้นตรงๆ ซึ่งแม่นยำ 100%
เพราะมันบอกตารางของตัวเองมาแล้ว

### ชั้น 4 — ตัวเลขทุกตัวต้องมาจาก material

โมเดลห้ามคิดเลข กฎเดียวกับผู้ช่วยคะแนนใน kai-proctor และมาจากเหตุการณ์เดียวกัน:
ได้ digest ที่เขียนว่า "26 ตาราง" มันคัดลอกรายการออกมา **แล้วนับแถวที่ตัวเองพิมพ์
รายงานเป็น 22** ทุกชื่อตารางที่มันเอ่ยมีจริง แต่ยอดรวมไม่จริง — และยอดรวมคือส่วนที่
คนเอาไปใช้ประชุม

ตัวตรวจไม่ได้คำนวณเลขที่ถูกให้ ซึ่งเป็นประเด็น: บริการไม่รู้ว่าคำตอบ*ควร*เป็นเท่าไร
รู้แค่ว่าเลขตัวนี้ถูก**ผลิต**ขึ้นแทนที่จะถูก**อ่าน** และเลขที่ผลิตเองย้อนกลับไปหา schema ไม่ได้
ตอนมีคนขอให้อธิบายที่มา

เลขนำหน้ารายการ (`1.` `2.` ต้นบรรทัด) ถูกตัดออกก่อนตรวจ — ไม่งั้นตัวตรวจจะเด้งใส่
คำตอบที่ถูกพอๆ กับคำตอบที่ผิด ซึ่งคือวิธีที่ guard ถูกปิดทิ้ง

## คำถามเรื่อง "ชุด" — ปัญหาที่คำตอบถูกทุกบรรทัดแต่ผิดทั้งคำตอบ

ถาม *"ตารางไหนบ้างที่มีข้อมูลอ่อนไหว"* คำตอบที่ถูกคือ **26 ตาราง** แต่ retriever ส่งให้
โมเดล 4 chunk **ทั้งสี่ถูกต้อง** และคำตอบที่ได้จะเอ่ย 4 ตารางโดยไม่มีอะไรบอกว่าไม่ครบ

**นี่แย่กว่าตอบผิด** คำตอบผิดจะถูกจับได้ครั้งแรกที่มีคนตรวจ แต่คำตอบที่เอ่ย 4 จาก 26
อ่านแล้วเหมือนครบ ถูกเอาไปใช้กำหนดขอบเขต migration แล้วอีก 22 ตารางถูกพบทีหลัง
โดยคนที่ต้องรับผลของมัน

### digest — รายการครบที่คำนวณตอน build

[`ingest/digest.py`](ingest/digest.py) สร้าง 5 รายการที่คลังระบุได้ **แน่นอน**

| digest | เนื้อหา |
|---|---|
| `digest_sensitive_columns` | 26 ตาราง 62 คอลัมน์ ที่จัดชั้น sensitive |
| `digest_tables` | ตารางทั้งหมด 192 ตาราง พร้อมจำนวนคอลัมน์ |
| `digest_unindexed_tables` | 17 ตารางที่ไม่ได้นำข้อมูลแถวเข้าดัชนี พร้อมเหตุผล |
| `digest_routes` | 98 กลุ่ม รวม 427 route |
| `digest_source_files` | 223 ไฟล์ในดัชนี และ **ตัดออก 253 ไฟล์** |

digest ไม่ใช่ "สรุป" แต่คือ**รายการทั้งหมด และมันบอกจำนวนของตัวเอง** เพราะสรุปที่ไม่ระบุ
ความครบถ้วนก็มีปัญหาเดียวกับ 4 chunk เดิม

**สิ่งที่ระบุแน่นอนไม่ได้ ไม่มี digest** ไม่มีรายการ "ไฟล์ไหนแตะฐานข้อมูลบ้าง" เพราะตัวสกัด
ของ export หาเจอแค่ 172 จาก 476 ไฟล์ — รายการที่อ้างว่าครบตรงนั้นคือความล้มเหลว
แบบเดียวกับที่ digest มีไว้เพื่อป้องกัน

**ให้ทีละใบ ไม่ใช่ทีเดียวสามใบ** ตอนแรกใส่ทั้ง 3 รายการเข้าไปพร้อมกัน โมเดลหยิบผิดใบแล้ว
ตอบ *2 จาก 26 ตาราง* อย่างหน้าตาเฉย — รายการครบช่วยได้ต่อเมื่อมันเป็น **"ใบนั้น"** อย่าง
ไม่กำกวม ซึ่งการจัดอันดับรู้อยู่แล้วว่าใบไหน

**และไม่ให้โมเดลพิมพ์รายการซ้ำ** `/ask` คืน field `lists` ที่มีเนื้อรายการเต็มให้ผู้เรียกไป
แสดงข้างคำตอบ ส่วน prompt สั่งให้บอกยอดรวมและยกตัวอย่าง 3–4 รายการพอ — วิธีเดียวกับที่
kai-proctor เลิกส่ง URL ให้โมเดล: **ไม่ให้มันพิมพ์สิ่งที่มันพิมพ์ผิดได้**

### ตาข่ายรอง — บอกเมื่อสิ่งที่ให้ไปเป็นแค่ตัวอย่าง

สำคัญกว่า digest เพราะ digest ครอบคลุมเฉพาะชุดที่คิดล่วงหน้าได้ ส่วนนี้ครอบคลุมที่เหลือ
ทั้งหมด — ถ้าจำนวน chunk ที่แมตช์มากกว่าที่แสดง จะต่อท้าย material ว่า

> ข้อมูลที่ให้มาข้างบนมี N รายการ แต่ในระบบมีอีกรวม M รายการที่ตรงกับคำถามนี้ —
> ที่แสดงคือตัวอย่างที่ตรงที่สุด ไม่ใช่รายการครบ ... ห้ามสรุปจำนวนรวมจากสิ่งที่เห็น

### สิ่งที่การวัดหักล้าง

**"แก้ prompt แล้วดีขึ้น" พิสูจน์ไม่ได้** ผมแก้ prompt ให้ขึ้นต้นด้วยยอดรวม แล้ววัดรอบเดียว
เห็น gemma4 ขึ้น 1 คะแนน qwen2.5 ลง 1 คะแนน — พอวัด 3 รอบถึงรู้ว่า **qwen2.5 ให้ 9, 8, 8
บน prompt เดิมอยู่แล้ว** ความต่าง 1 คะแนนจึงไม่ใช่หลักฐานของอะไรเลย ตอนนี้ `--repeat`
รายงานเป็นช่วง ต่ำ–สูง และบอกด้วยว่าคำถามข้อไหนผลแกว่ง

**คำตอบว่างเปล่าเคยถูกส่งกลับเป็น `ok: true`** gemma4 ตอบว่างใน 2 จาก 10 ข้อ — HTTP 200,
body ถูกรูปแบบ, ข้างในไม่มีอะไร guard ทุกชั้นผ่านหมดเพราะไม่มีอะไรให้ตรวจ ตอนนี้
`llm.ask()` โยน `llm_empty` และตัด `<think>` ของโมเดลคิดก่อนตอบทิ้งก่อนเสมอ

## ข้อจำกัดที่รู้อยู่

**คำที่ไม่อยู่ใน lexicon = คำถามที่ถูกปฏิเสธ** นี่คือราคาที่จ่ายเพื่อกันคำถามนอกเรื่อง
ถามด้วยคำที่ไม่มีในทั้งสองพจนานุกรมจะได้ `off_topic` แม้คลังจะตอบได้ — เป็นความล้มเหลว
ที่เลือกแล้ว เพราะมันมองเห็นได้และคนที่เจอรายงานคำที่ขาดได้ ต่างจากคำตอบมั่นใจที่ประกอบ
จากอะไรก็ตามที่บังเอิญติดอันดับ ซึ่งคนที่ถูกหลอกมองไม่เห็น
**เพิ่มคำใน [`app/lexicon.py`](app/lexicon.py) ได้ตลอด**

**คอลัมน์ชื่อคำเดียวยังไม่ถูกตรวจ** (`id`, `status`, `ordering`) ดูชั้น 3 ข้างบน

**"ดัชนี" กำกวม** ใน lexicon มันหมายถึง database index แต่ผู้ใช้อาจหมายถึงดัชนีค้นหาของ
ผู้ช่วยเอง — ถาม *"ตารางไหนที่ไม่ได้เอาข้อมูลเข้าดัชนี"* จะได้ตารางที่มี index แทนที่จะได้
`digest_unindexed_tables`

**foreign key มีแค่ 28 รายการจาก 192 ตาราง** ฐานข้อมูลนี้แทบไม่ประกาศ referential
integrity ความสัมพันธ์ที่เหลือถูกบังคับในโค้ด ผู้ช่วยจึงบอก join ได้ไม่ครบ และ chunk
`foreign_keys` ระบุข้อจำกัดนี้ไว้ในตัวมันเองเพื่อไม่ให้ 28 รายการถูกอ่านว่าครบแล้ว

**ตัวสกัดหาตารางเจอใน 172 จาก 476 ไฟล์** chunk ที่ไม่เจอเขียนกำกับไว้ว่า "ตัวสกัดไม่พบ
(ไม่ได้แปลว่าไฟล์นี้ไม่แตะฐานข้อมูล)" แทนที่จะปล่อยว่าง — ช่องว่างที่ไม่มีคำอธิบายจะถูกอ่าน
ว่าเป็นข้อเท็จจริง
