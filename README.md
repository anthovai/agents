## บันทึกการเรียนเป็นครั้งๆ (sitting)

ทุกครั้งที่มีการเฝ้าดู ระบบเปิด **sitting** หนึ่งรายการ แล้วผูกผลตรวจ หลักฐาน
และสัญญาณทั้งหมดของครั้งนั้นไว้ด้วยกัน — บอกได้ว่าอันไหนคือการนั่งเรียนครั้งไหน

แต่ละ sitting เก็บ **นโยบายที่บังคับใช้ ณ ตอนเริ่ม** ไว้เป็น snapshot รวมถึงเกณฑ์
เทียบใบหน้า ผู้ดูแลแก้การตั้งค่าทีหลัง **ไม่เปลี่ยนความหมายของครั้งที่ผ่านมาแล้ว**
— เป็นคำตอบให้กับคำถามที่ผู้เรียนอาจถามหลายเดือนต่อมาว่า "ตอนนั้นระบบตั้งกฎอะไรไว้"

นโยบายถูกอ่านจาก server ตอนเปิด sitting แล้วส่งกลับไปให้เบราว์เซอร์ใช้ ไม่ใช่ให้
เบราว์เซอร์บอกว่าใช้กฎอะไร — ไม่งั้น snapshot จะพิสูจน์อะไรไม่ได้เลย

| สถานะ | หมายถึง |
|---|---|
| `active` | กำลังเรียนอยู่ |
| `completed` | จบจริง (วิดีโอจบ หรือส่งข้อสอบแล้ว) |
| `terminated` | ระบบตัดจบ พร้อมเหตุผล |
| `abandoned` | หยุดเฝ้าดูโดยไม่มีอะไรยืนยันว่าจบ (ปิดเครื่อง เน็ตหลุด) |

การออกจากหน้าเว็บ **ไม่** ถูกนับว่า `completed` เพราะเบราว์เซอร์แยกไม่ออกระหว่าง
รีโหลด เน็ตหลุด และเลิกกลางคัน — scheduled task จะปิดให้เป็น `abandoned` แทน
ซึ่งบันทึกเฉพาะสิ่งที่รู้จริง และ `completed` ที่มาทีหลังไม่สามารถทับ `terminated` ได้

## นำเข้าข้อสอบจาก PDF

แนวข้อสอบใบอนุญาตของไทยแจกเป็น PDF และไม่มีทางอื่นที่จะเอาเข้าคลังข้อสอบ
นอกจากพิมพ์ใหม่ทั้งชุด — Moodle ไม่มีความสามารถนี้

เปิดจากเมนูในคอร์ส หรือ `/local/kaiproctor/import.php?courseid=`

รองรับรูปแบบ: ข้อสอบขึ้นต้น `1.` ตัวเลือก `( ) ก.` เฉลยขึ้นต้น `คำตอบ : วิชา`
ระดับความยากไม่มีในไฟล์ ระบบแบ่งเป็นสามส่วนแล้วเก็บเป็น **tag** ของข้อสอบ
ซึ่ง Moodle ใช้สุ่มข้อสอบตาม tag ได้ — จึงยังทำ blueprint ตามความยากได้เหมือนเดิม

**ต้องดูตัวอย่างก่อนนำเข้าเสมอ** หน้าจอบังคับให้ดู 3 ข้อแรกพร้อมเฉลยก่อนกดยืนยัน
เพราะการอ่าน PDF ภาษาไทยยังมีข้อจำกัด (ดูด้านล่าง)

### ข้อจำกัดที่ต้องรู้

การสกัดข้อความไทยจาก PDF ประกอบบรรทัดได้ถูกต้อง แต่**ลำดับสระกับวรรณยุกต์ที่ซ้อนบน
พยัญชนะตัวเดียวกันยังสลับได้** (เช่น `ผู้` อาจออกมาเป็น `ผ้เู`) เพราะทั้งคู่กว้างศูนย์
และใช้พิกัดเดียวกัน การแก้ให้ถูกทุกกรณีต้องอ่าน shaping table ของฟอนต์ ไม่ใช่แค่ตำแหน่งกลิฟ

ตัวเลือกและเฉลยไม่ได้รับผลกระทบ — สิ่งที่กระทบคือความสวยงามของข้อความ
ผู้นำเข้าต้องอ่านตัวอย่างและแก้ในคลังข้อสอบถ้าจำเป็น

> ของเดิมใช้ **PyMuPDF ซึ่งเป็น AGPL-3.0** เปลี่ยนเป็น **pdfminer.six (MIT)** แล้ว
> ปัญหาไลเซนส์แบบเดียวกับ InsightFace

## Safe Exam Browser

ข้อสอบ **"ความเสี่ยงสูง (SEB)"** เปิดทั้งสองชั้นพร้อมกัน:

- **SEB** ล็อกเครื่อง — Moodle สร้างไฟล์ `.seb` และ **Config Key** ให้เอง (ของจริง ไม่ใช่ hash ที่ทำเอง)
- **ระบบเรา** ยืนยันตัวตนและเก็บหลักฐาน

เปิดจากเบราว์เซอร์ธรรมดาไม่ได้ ต้องกดลิงก์ `seb://` ซึ่ง SEB ที่ติดตั้งบนเครื่องจะรับช่วงต่อ

> ชั้น lockdown ในเบราว์เซอร์ของเรา **ตรวจจับและบันทึก** เท่านั้น ห้าม Alt+Tab จอที่สอง
> หรือมือถือข้างๆ ไม่ได้จริง ถ้าต้องการล็อกจริงต้องใช้ SEB

ทุกโมเดลที่ใช้ต้องใช้เชิงพาณิชย์ได้ ดู [face-service/models/LICENSES.md](face-service/models/LICENSES.md)

## ⚠️ ยังไม่ได้ปรับเทียบเกณฑ์ใบหน้า

`FACE_MATCH_THRESHOLD=0.363` เป็นค่าอ้างอิงของผู้พัฒนา SFace **ไม่ใช่ค่าที่ปรับเทียบกับข้อมูลจริง**
โปรเจคเดิมก็ไม่เคยปรับเทียบเช่นกัน (`face-re/tests/images/` ที่ smoke test อ้างถึงไม่เคยมีอยู่จริง —
เทสต์ 36 ตัวที่ผ่านใช้กล้องปลอมที่ไม่มีใบหน้า จึงพิสูจน์ flow ได้ แต่ไม่พิสูจน์ความแม่นยำ)

ก่อนใช้งานจริงต้อง:

1. ใส่ภาพลงทะเบียนจริงใน `face-service/tests/faces/` ชื่อ `<คน>_<ลำดับ>.jpg`
2. `pytest tests/test_calibration.py -s -m calibration`
3. เอาค่าที่ได้ไปใส่ `FACE_MATCH_THRESHOLD`

## สุ่มข้อสอบซ้ำได้ และพิสูจน์ว่าไม่ได้เลือกไว้ก่อน

ข้อสอบที่ตั้ง random slot ตาม tag ความยาก จะถูกสุ่มด้วย seed ที่คำนวณจาก
**ผู้เรียน + ข้อสอบ + ลำดับครั้งที่สอบ** เท่านั้น ไม่มี timestamp ไม่มี secret ของไซต์

ผลที่ได้คือสองอย่างที่ต่างกัน และควรแยกให้ชัด:

- **seed เลือกไม่ได้** ใครก็ตามที่มีสามค่านั้นคำนวณซ้ำเพื่อตรวจได้ หน้ารายงานคำนวณซ้ำให้ทุกครั้ง
  และขึ้นป้ายแดงถ้าไม่ตรง คุณสมบัตินี้เป็นจริงตลอดไป
- **สุ่มซ้ำได้เฉพาะบน Moodle เวอร์ชันเดิมและคลังข้อสอบเดิม** คลังถูกแก้หรือ core อัปเกรดเมื่อไร
  ก็สุ่มซ้ำไม่ได้ — หลักฐานที่คงทนคือ **รายการข้อสอบที่บันทึกไว้** ไม่ใช่ความสามารถในการสุ่มซ้ำ

ทำได้โดยไม่แตะ core: `notify_preflight_check_passed()` ทำงานก่อน mod_quiz สร้าง attempt พอดี
และตัวโหลดข้อสอบใช้ `shuffle()` ซึ่งใช้ MT engine ของ PHP

## ผู้ช่วย AI — เป็นบริการแยก

ปิดไว้เป็นค่าเริ่มต้น ไม่มีส่วนไหนของระบบพึ่งพา
ดู [docs/AI.md](docs/AI.md) และสัญญาการเชื่อมต่อที่ [docs/AI-CONTRACT.md](docs/AI-CONTRACT.md)

สรุปการเรียนแต่ละครั้งให้ผู้ตรวจอ่าน และชี้ข้อสอบที่ข้อความไทยเพี้ยนจากการนำเข้า PDF

```
LMS ──POST /summarise──> ai-service ──> Ollama บนเครื่องนี้ (ค่าเริ่มต้น)
     payload contract 1.0              หรือ GPT-5 mini
```

**ไม่ได้อยู่ในปลั๊กอินอีกแล้ว** เพราะลูกค้าที่เอาซอร์สไปดูแลเองจะแก้ guardrail ได้
และแก้ payload ให้กว้างขึ้นได้ ทั้งที่สรุปยังมีชื่อเราติดอยู่ พอเป็นบริการ
"ไม่มีข้อมูลชีวมิติออกไป" เปลี่ยนจากคำสัญญาเรื่องวินัยของผู้เรียก เป็นโค้ดใน
`ai-service/app/contract.py` ที่เราดูแล — ผู้เรียกส่งผิดได้ `422` ไม่ใช่การรั่วเงียบๆ

**กฎที่บังคับด้วยรูปทรงข้อมูล** `checks`/`events`/`evidence` รับเฉพาะจำนวนเต็ม
และคะแนน similarity/liveness/confidence เป็นทศนิยมทั้งหมด — payload จึงปฏิเสธมันเอง
โดยไม่ต้องเดาชื่อฟิลด์ เป็นกฎเดียวที่ทนต่อการเปลี่ยนชื่อฟิลด์เพื่อเลี่ยงตัวกรองคำ

**ตรวจคำตอบด้วย ไม่ใช่แค่สั่งใน prompt** วัดกับ qwen2.5:7b แล้วคำสั่งห้ามตัดสิน
เอาอยู่แค่ 1 ใน 5 ครั้ง โมเดลชอบเขียนว่า *"ยังไม่มีหลักฐานชัดเจนว่าเกิดจากการกระทำผิด"*
ซึ่งคือคำพิพากษาในรูปการปฏิเสธ ตอนนี้บริการอ่านคำตอบก่อนส่งออก เจอแล้วถามใหม่
ยังเจออยู่ก็ตอบ `guardrail_violation` — ผู้ตรวจไม่มีวันเห็นสรุปที่ตัดสิน

> **ตรวจข้อความไทยเพี้ยนยังใช้กับโมเดลบนเครื่องไม่ได้** จับข้อที่เสียได้ 6/6
> แต่ฟ้องข้อที่สะอาดผิดด้วย 6/6 ต้องรอทดสอบกับ GPT-5 mini ก่อน
> ส่วนสรุปรายครั้งใช้ได้ปกติ

**ค้นจาก Moodle สดๆ ไม่ได้ทำดัชนีแช่ไว้** เพราะการลงทะเบียน กลุ่ม เงื่อนไขวันเวลา
และการซ่อนกิจกรรม เป็นตัวตัดสินว่าหน้านั้น "มีอยู่" สำหรับคนนี้หรือเปล่า —
ดัชนีที่ export ออกมาจะไม่รู้เรื่องพวกนี้ และจะเริ่มบอกใบ้ถึงหน้าที่คนถามเปิดไม่ได้

**ไม่มีคอร์สของคนอื่นอยู่ในดัชนีเลย** การตอบว่า "คุณไม่ได้ลงทะเบียนคอร์ส X"
ก็คือการเปิดเผยว่าคอร์ส X มีอยู่ — ระบบจึงไม่เคยเห็นมันตั้งแต่แรก แทนที่จะเห็นแล้วปฏิเสธ

**ไม่เจอ = ไม่เรียกโมเดลเลย** โมเดลที่ได้คำถามโดยไม่มีเนื้อหาประกอบจะตอบอยู่ดีจาก
สิ่งที่เรียนมาจากที่อื่น ตัดสินใจในโค้ดถูกกว่าและแน่นอนกว่าการขอให้โมเดลปฏิเสธเอง

**ลิงก์ที่แต่งขึ้นเองถูกทิ้ง** บริการเทียบทุกลิงก์ในคำตอบกับรายการที่ส่งไป ไม่ตรงคือ
ถามใหม่ ยังไม่ตรงก็ตอบ `invented_link` — ลิงก์ที่กดแล้ว 404 ทำให้ผู้เรียนเลิกเชื่อทั้งฟีเจอร์

การค้นใช้ **character trigram** ไม่ใช่การตัดคำ เพราะภาษาไทยไม่มีช่องว่าง
วิธีตัดคำต้องมีพจนานุกรม และเวลาผิดมันจะเงียบ — คือหาไม่เจอเฉยๆ โดยไม่มีใครรู้


## ผู้ช่วยตอบเรื่องข้อสอบและคะแนนได้

ถามได้ว่า *"ฉันสอบผ่านไหม"* *"ข้อสอบนี้ได้กี่คะแนน"* *"ยังสอบได้อีกกี่ครั้ง"*
*"ข้อสอบปิดรับเมื่อไหร่"*

อ่านจาก**สมุดคะแนน** ไม่ใช่ตารางการสอบ และดึงสดตอนตอบ ไม่ได้แคชไว้ — คนที่เพิ่งส่ง
ข้อสอบเสร็จต้องไม่ถูกบอกคะแนนของสัปดาห์ที่แล้ว

**ของตัวเองเท่านั้น** contract ไม่มีคีย์สำหรับผู้เรียนคนอื่น ไม่มีค่าเฉลี่ยห้อง ไม่มีชื่อคน
— โมเดลเปิดเผยสิ่งที่ไม่เคยได้รับไม่ได้ แม้จะถูกถามตรงๆ

**โมเดลห้ามคิดเลข** ทุกตัวเลขรวมร้อยละคำนวณใน PHP แล้วส่งไปเป็นค่าสำเร็จ บริการ
เทียบตัวเลขทุกตัวในคำตอบกับที่ส่งไป ไม่ตรงคือทิ้ง — ตัวเลขที่โมเดลคำนวณเองย้อนกลับไป
หาสมุดคะแนนไม่ได้ และเป็นตัวเลขที่ผู้เรียนจะยกไปร้องเรียน

**รายงาน ไม่ใช่ตัดสิน** บอกว่าผ่านได้เพราะ*เกณฑ์ผ่านเป็นกฎที่ครูตั้งและสมุดคะแนน
ตัดสินไปแล้ว* — คนละเรื่องกับผู้ช่วยผู้ตรวจที่ห้ามตัดสินเรื่องทุจริต ซึ่งกฎนั้นไม่ถูกแตะ

> **สิ่งที่ออกจากไซต์เปลี่ยนไป** เดิมมีแต่ชื่อเหตุการณ์และจำนวนครั้ง ตอนนี้มีคะแนน
> ของผู้ถามด้วย ค่าเริ่มต้นยังเป็นโมเดลบนเครื่องตัวเอง และหน้าคอนโซลเตือนแล้ว
> ถ้าปลายทางอยู่นอกเครือข่าย


## วิดีโอแบบมีปฏิสัมพันธ์ของเราเอง — `mod_kaivideo`

`mod_interactivevideo` ยังติดตั้งอยู่ข้างๆ ไม่ได้ถอด — แต่สิ่งที่มันเป็นไม่ได้คือ **เป็นของเรา**
ลูกค้าต้องตรวจสอบทั้งสามชิ้นที่ซื้อไป และปลั๊กอินของคนอื่น*อ่านได้*แต่เรา*รับผิดชอบแทนไม่ได้*

ดู [docs/INTERACTIVE-VIDEO.md](docs/INTERACTIVE-VIDEO.md)

แยกส่วนแบบเดียวกับ face recognition: ข้อมูลและการตัดสินอยู่ใน PHP ที่ตรวจได้โดยไม่ต้องมี
เบราว์เซอร์ ส่วน player เป็นชิ้นเดียวที่ต้องเป็น UI

**เฉลยไม่เคยออกไปที่เบราว์เซอร์ก่อนตอบ** — และมีเทสต์อ่าน HTML ของหน้าจริงเพื่อยืนยัน
ไม่ใช่อ่าน API เพราะคนที่จะโกงเปิด developer tools

**ลากแถบเวลาข้ามคำถามไม่ได้** คำถามถือว่าถึงกำหนดเมื่อหัวเล่นอยู่ที่หรือเลยจุดนั้นแล้ว
และยังไม่ได้ตอบ ทำให้เล่นปกติ ลากแถบ และกลับมาเรียนต่อ เป็นกรณีเดียวกันหมด

**การคุมสอบทำงานทันทีโดยไม่ต้องเขียนอะไรเพิ่ม** เพราะ player เป็น `<video>` element จริง
ซึ่ง attention monitor ขับได้อยู่แล้ว — เป็นเหตุผลที่ตั้งใจไม่ใช้ iframe embed


## วัดภาระโหลดของ face-service แล้ว

`reports/FACE-LOAD.txt` — ยิง `/analyze` ด้วยภาพจริงที่ concurrency 1 ถึง 32
**ไม่มีคำขอไหนล้มเหลวเลย** แต่ p95 ขยับจาก 0.28 วินาที เป็น 7.08 วินาที

ตัวเลขเดียวกันอ่านได้สองแบบ และแบบที่ฟังดูดีคือแบบที่ใช้วางแผนไม่ได้:

| | รับได้ประมาณ |
|---|---|
| ดูบทเรียนที่มีการเฝ้าดู | **~600 คน** (คนละ 1 คำขอ ต่อ 120 วินาที) |
| **ลงทะเบียนใบหน้าพร้อมกัน** | **~1–2 คน** |

**การลงทะเบียนคือคอขวด และเป็นตัวเลขที่ต้องใช้วางแผน** เพราะ liveness challenge
ยิง `/analyze` วินาทีละหลายครั้ง**ต่อคน** ตลอดเวลาที่หันหน้า — คน 100 คนที่เริ่มสอบพร้อมกัน
คือคน 100 คนที่ลงทะเบียนพร้อมกัน และ challenge ที่รอ 7 วินาทีต่อเฟรมทำไม่สำเร็จ

> เป็นเพดานของ face pipeline เท่านั้น ไม่รวม Moodle ฐานข้อมูล การเขียนหลักฐาน และเบราว์เซอร์
> และวัดบนแล็ปท็อปที่รันทุกอย่างอยู่พร้อมกัน — ใช้เป็นลำดับความใหญ่ ไม่ใช่แผนความจุ

> **bench เวอร์ชันแรกส่ง JSON ไปที่ endpoint ที่รับ multipart** ทุกคำขอถูกปฏิเสธในไม่ถึงมิลลิวินาที
> และมันจะรายงาน **427 req/s** ซึ่งเป็นเรื่องโกหกที่ดูเหมือนข่าวดี — ตัวนับ failure คือสิ่งเดียวที่กันไว้
