# คู่มือผู้ดูแลระบบ

สำหรับคนที่ดูแลระบบนี้อยู่ทุกวัน ไม่ใช่คนที่ติดตั้ง (นั่นคือ [DEPLOY.md](DEPLOY.md))

---

## ดูอะไรก่อนทุกเช้า

`/local/kaiproctor/stats.php` — ต้องมีสิทธิ์ `local/kaiproctor:manage`

หน้านี้เตือนเสียงดังสองเรื่อง เพราะทั้งสองเงียบแล้วอันตราย:

| คำเตือน | แปลว่า | ต้องทำอะไร |
|---|---|---|
| 🔴 **ไม่พบโมเดล liveness** | ระบบยังทำงานปกติ **แต่ภาพถ่ายที่ถือมาส่องกล้องจะผ่านหมด** | รัน `sh face-service/models/fetch.sh` แล้ว restart face-service |
| 🔴 **มีหลักฐานเก่ากว่าระยะเก็บรักษา** | **cron ไม่ทำงาน** และหน้าที่ตาม PDPA ไม่ถูกปฏิบัติ | ดูหัวข้อ "cron ไม่ทำงาน" |

ถ้าสองอันนี้เขียว ระบบทำหน้าที่ของมันอยู่

## เรื่องที่ผู้เรียนโทรมาถามบ่อยที่สุด

### "ลงทะเบียนใบหน้าไม่ผ่าน"

**ข้อความบนหน้าจอบอกสาเหตุจริง** อ่านตรงนั้นก่อน แต่ละแบบต้องแก้คนละอย่าง:

| ข้อความ | สาเหตุ | บอกผู้เรียนว่า |
|---|---|---|
| กล้องหาใบหน้าไม่พบ | ไม่มีใบหน้าในเฟรม หรือมีอะไรบัง | นั่งหันหน้าเข้ากล้อง เอาหน้ากาก/หมวกออก |
| ใบหน้าเล็กเกินไปในภาพ | นั่งไกลกล้องเกินไป | ขยับเข้าใกล้ |
| มีใบหน้ามากกว่าหนึ่งในภาพ | มีคนอื่น หรือ**ภาพถ่าย/จอด้านหลัง** | ให้อยู่คนเดียวในกรอบ |
| ยืนยันไม่ได้ว่าเป็นคนจริง | liveness ไม่ผ่าน | ใช้กล้องของตัวเอง มองตรงเข้ากล้อง ไม่ใช่ส่องภาพถ่าย |
| หันหน้าไม่ทันเวลา | ทำท่าไม่ทัน | หันช้าๆ ตามที่หน้าจอบอก |

> ระบบ**ไม่ได้วัดแสง**เลย ถ้าใครบอกว่า "ระบบบอกว่าห้องมืด" นั่นคือข้อความเก่าที่แก้ไปแล้ว —
> ให้อัปเดตเป็นเวอร์ชันปัจจุบัน

### "กล้องไม่ทำงานเลย"

ไล่ตามลำดับนี้:

1. **หน้าเว็บเป็น HTTPS หรือเปล่า** เบราว์เซอร์ห้าม `getUserMedia` บน http:// เด็ดขาด
2. ผู้เรียนกด "อนุญาต" ตอนเบราว์เซอร์ถามหรือยัง — ถ้ากดปฏิเสธไปแล้ว ต้องแก้ที่ไอคอนกล้อง
   บนแถบที่อยู่
3. มีโปรแกรมอื่นถือกล้องอยู่ไหม (Zoom, Teams, OBS)

### "สอบอยู่แล้วโดนตัดจบ"

เปิดหน้ารายงานของผู้เรียนคนนั้น — เมนู "การคุมสอบ" ในกิจกรรม หรือ
`/local/kaiproctor/report.php?userid=<id>&contextid=<id>`

รายงานบอก **เหตุผลที่ตัดจบ** และ **นโยบายที่บังคับใช้อยู่ตอนนั้น** ซึ่งเป็นคนละอย่างกับ
นโยบายวันนี้ — ถ้ามีคนแก้การตั้งค่าหลังจากนั้น การเรียนครั้งเก่าไม่เปลี่ยนความหมาย

## cron ไม่ทำงาน

อาการ: หลักฐานไม่ถูกลบ ดิสก์โต หน้าสถิติขึ้นเตือนแดง

```bash
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env ps cron
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env logs --tail 50 cron
```

สั่งล้างเดี๋ยวนั้น:

```bash
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env \
  exec moodle php /var/www/html/admin/cli/scheduled_task.php \
  --execute='\local_kaiproctor\task\purge_evidence'
```

**อย่าปิด cron ทิ้งไว้** งานที่ค้างไม่ใช่แค่การล้างหลักฐาน — Moodle ใช้ cron ส่งอีเมล
คิดคะแนน และปิด sitting ที่ค้างเป็น "abandoned" ด้วย

## ผู้เรียนขอดู หรือขอลบข้อมูลของตัวเอง (PDPA)

ใช้กลไกของ Moodle เอง ไม่ต้องแตะฐานข้อมูล:

**Site administration → Users → Privacy and policies → Data requests**

- **ขอดู/ขอสำเนา** — ระบบรวบรวมให้ทั้งค่าที่แทนใบหน้า ผลตรวจแต่ละครั้ง ภาพและคลิปหลักฐาน
- **ขอลบ** — ลบทั้งแถวในฐานข้อมูล **และไฟล์บนดิสก์**

> ตอนแรกการลบทิ้งไฟล์หลักฐานไว้บนดิสก์ ลบแค่แถวในตาราง — เป็นบั๊ก PDPA จริงที่แก้แล้ว
> ถ้าคุณรันเวอร์ชันเก่ากว่านั้น ให้อัปเกรดก่อนรับคำขอลบ

**ห้ามลบด้วยการ DELETE ในฐานข้อมูลเอง** เพราะไฟล์จะค้าง และไม่มีบันทึกว่าลบเมื่อไหร่
โดยใคร ซึ่งเป็นสิ่งที่ต้องแสดงได้เวลาถูกตรวจ

## เปิด/ปิดผู้ช่วย AI

`/local/kaiproctor/ai.php` — Site administration → Plugins → Local plugins → ผู้ช่วย AI

หน้านี้บอกสิ่งที่ต้องรู้ก่อนตัดสินใจ ไม่ใช่แค่สวิตช์:

- โมเดลไหนตอบงานไหน
- ปลายทางอยู่ที่ไหน และ **เป็นเครื่องที่คุณควบคุมเองหรือของคนอื่น**
- บริการติดต่อได้หรือเปล่า

**⚠️ ถ้าปลายทางอยู่นอกเครือข่าย หน้าจะขึ้นเตือนสีเหลือง** — ข้อมูลกิจกรรมผู้เรียน
รวมถึง**คะแนนของผู้เรียนที่ถามถึงตัวเอง** จะถูกส่งออกไป ตรวจกับเอกสารความยินยอมและ
สัญญาประมวลผลข้อมูลก่อนเปิด

**ไม่มีภาพ ไม่มีคลิป ไม่มีค่าวัดใบหน้า ออกไปไม่ว่ากรณีใด** บริการปฏิเสธ payload
ที่มีสิ่งเหล่านั้นที่ขอบเขต ไม่ใช่กรองทิ้ง

ปิดอยู่เป็นค่าเริ่มต้น และไม่มีส่วนไหนของระบบพึ่งพา — ปิดแล้วทุกอย่างทำงานครบเหมือนเดิม

## เปิดการเฝ้าดูให้กิจกรรมหนึ่ง

ในกิจกรรมนั้น → เมนู **"การคุมสอบ"**

รองรับ: วิดีโอแบบมีปฏิสัมพันธ์ (ของเราและของ mod_interactivevideo), H5P, หน้าเนื้อหา,
ไฟล์, ลิงก์

**ผู้สอนที่เปิดดูกิจกรรมจะไม่ถูกเฝ้าดู** — คนตรวจงานไม่ใช่คนสอบ

ส่วนข้อสอบใช้คนละกลไก: ตั้งที่ **การตั้งค่าแบบทดสอบ → ข้อจำกัดเพิ่มเติม → KAISER Proctor**

## นำเข้าข้อสอบจาก PDF

ในคอร์ส → **นำเข้าข้อสอบจาก PDF** หรือ `/local/kaiproctor/import.php?courseid=`

**ต้องดูตัวอย่างก่อนนำเข้าเสมอ** — หน้าจอบังคับให้ดู 3 ข้อแรกพร้อมเฉลย เพราะการอ่าน
ภาษาไทยจาก PDF ยังมีข้อจำกัด: สระกับวรรณยุกต์ที่ซ้อนบนพยัญชนะตัวเดียวกันสลับกันได้
(เช่น `ผู้` ออกมาเป็น `ผ้เู`) ตัวเลือกและเฉลยไม่ได้รับผลกระทบ แต่ข้อความอาจต้องแก้ในคลังข้อสอบ

## เปลี่ยนเกณฑ์เทียบใบหน้า

Site administration → Plugins → Local plugins → KAISER Proctor

**สิ่งที่ต้องเข้าใจก่อนแก้:** การแก้ค่านี้**ไม่เปลี่ยนความหมายของการเรียนครั้งที่ผ่านมาแล้ว**
ทุก sitting เก็บ snapshot ของนโยบายตอนเริ่มไว้ รวมถึงเกณฑ์ที่ใช้ตัดสิน — เป็นคำตอบให้กับ
คำถามที่ผู้เรียนอาจถามหลายเดือนต่อมาว่า "ตอนนั้นระบบตั้งกฎอะไรไว้"

> ค่าที่ให้มายังไม่ได้ปรับเทียบ ดู [FACE-VALIDATION.md](FACE-VALIDATION.md)
> ก่อนใช้ตัดสินอะไรที่มีผลกับคน

## คำสั่งที่ใช้บ่อย

ทั้งหมดรันจากโฟลเดอร์โปรเจค บนเซิร์ฟเวอร์

```bash
export C="docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env"
```

| ต้องการ | คำสั่ง |
|---|---|
| ดูสถานะทุกบริการ | `$C ps` |
| ดู log ของ Moodle | `$C logs -f moodle` |
| รีสตาร์ทเฉพาะ face-service | `$C restart face-service` |
| ล้าง cache ของ Moodle | `$C exec moodle php /var/www/html/admin/cli/purge_caches.php` |
| สำรองข้อมูลเดี๋ยวนี้ | `sh deploy/backup.sh /var/backups/kaiproctor` |
| ดูว่า face service ตอบไหม | `$C exec moodle php -r '...'` หรือเปิดหน้าสถิติ |

## เมื่ออะไรพัง — ไล่ตามนี้

1. **หน้าสถิติขึ้นอะไร** ตอบได้เกินครึ่งของคำถาม
2. **`$C ps`** มีบริการไหนไม่ได้ `running`
3. **`$C logs --tail 100 <service>`** ของตัวที่ผิดปกติ
4. **ดิสก์เต็มหรือเปล่า** `df -h` — หลักฐานโตเงียบๆ ถ้า cron ไม่ทำงาน

ถ้ายังไม่เจอ ให้เก็บสามอย่างนี้ไว้ก่อนแจ้ง: log ของบริการที่ผิด, สิ่งที่หน้าสถิติแสดง,
และเวลาที่เกิดเหตุพร้อมชื่อผู้เรียนที่เจอปัญหา — สามอย่างนี้ทำให้ไล่ปัญหาได้เร็วกว่า
คำอธิบายอาการหลายย่อหน้า
