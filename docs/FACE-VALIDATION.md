# การตรวจสอบชั้นเทียบใบหน้า

เอกสารนี้แยกสองเรื่องที่ปนกันง่ายและผลลัพธ์ต่างกันสิ้นเชิง

| | คำถาม | ตอบได้แล้วหรือยัง |
|---|---|---|
| **Sanity check** | ระบบแยกคนออกจากกันได้จริงไหม | ✅ ตอบแล้ว |
| **Calibration** | เกณฑ์เท่าไรถึงเหมาะกับผู้เรียนและกล้องของเรา | ❌ **ยังไม่ได้ตอบ** |

---

## 1. Sanity check — ผ่านแล้ว

ใช้ภาพ **public domain** จาก Wikimedia Commons (ภาพราชการสหรัฐ ไม่มีลิขสิทธิ์)
ดึงด้วย `face-service/fetch-reference-faces.py` บันทึกที่มาไว้ใน
`face-service/tests/faces-public/CREDITS.md`

ภาพ 13 ใบ ใช้ได้ 6 ใบ จาก 3 คน:

| | ต่ำสุด | มัธยฐาน | สูงสุด |
|---|---|---|---|
| คู่ภาพ**คนเดียวกัน** | **0.7381** | 0.7942 | 0.9667 |
| คู่ภาพ**คนละคน** | 0.0871 | 0.2256 | **0.3051** |

คนเดียวกันต่ำสุด (0.7381) สูงกว่าคนละคนสูงสุด (0.3051) มาก — **แยกกันได้สะอาด**
สรุปได้ว่าท่อ YuNet → SFace → cosine similarity ต่อถูกต้อง ไม่ได้ต่อกลับด้าน

เส้นทางเต็มผ่าน Moodle web service ก็ทำงาน:

```
ENROL  ok
SAME   pass    similarity 0.7942   liveness 0.9997
OTHER  review  similarity 0.3051   liveness 0.9918
```

### บั๊กที่ตรวจเจอเพราะมีใบหน้าจริง

**`extract_face()` โยน exception ทุกครั้งที่เจอใบหน้าจริง**

`cv2.solvePnP` ค่าเริ่มต้นใช้ `SOLVEPNP_ITERATIVE` ซึ่งเริ่มด้วย DLT ที่ต้องการ
**6 จุด** แต่ YuNet ให้ landmark มา **5 จุด** → OpenCV 5.0 ไม่ได้คืนค่าแย่ๆ
แต่ **raise** ออกมาเลย

แปลว่า **การลงทะเบียนใบหน้าและการยืนยันตัวตนพังทั้งหมด** — และเทสต์ทั้ง 48 ตัว
จับไม่ได้ เพราะกล้องปลอมของ Chromium ไม่มีใบหน้าในภาพ โค้ดจึงไม่เคยเดินมาถึงบรรทัดนั้น

แก้เป็น `SOLVEPNP_SQPNP` (รองรับตั้งแต่ 3 จุด) และดักกรณีล้มเหลวให้คืนมุม 0
แทนที่จะพังการตรวจจับ — pose ใช้นำทาง liveness challenge ไม่ได้ใช้ตัดสินตัวตน
จึงไม่ควรทำให้ทั้งระบบล้ม

เพิ่มเทสต์กันย้อนกลับไว้ 2 ตัวใน `face-service/tests/test_face_engine.py`

## 2. Calibration — ยังไม่ได้ทำ

**ห้ามเอาเลข 0.5216 จาก sanity check ไปใช้**

ภาพชุดนั้นเป็นภาพถ่ายทางการและภาพข่าว ถ่ายด้วยกล้องมืออาชีพในแสงที่จัดมาแล้ว
ส่วนผู้เรียนจริงจะนั่งหน้าเว็บแคมราคาถูกในห้องที่แสงเป็นยังไงก็ตาม
คะแนนคู่ภาพคนเดียวกันในสภาพจริงจะ **ต่ำกว่า** 0.7381 มาก

ถ้าตั้ง 0.5216 แล้วเอาไปใช้จริง จะเกิดสิ่งที่แย่กว่าการไม่ปรับเทียบเลย คือ
**ตัวเลขที่ดูเหมือนผ่านการตรวจสอบแล้ว แต่วัดจากข้อมูลผิดชุด**

### ค่าที่ใช้อยู่ตอนนี้

```
FACE_MATCH_THRESHOLD=0.363   ค่าอ้างอิงของผู้พัฒนา SFace
FACE_REVIEW_MIN=0.30
```

จากผลข้างบนจะเห็นข้อจำกัดของค่าตั้งต้นชัดเจน: คนละคนได้ 0.3051 ซึ่งตกใน
**review band** (0.30–0.363) แทนที่จะเป็น `fail` ยังไม่ถือว่าเป็นช่องโหว่
เพราะไม่ผ่าน แต่ระยะห่างแคบเกินไปสำหรับระบบที่ต้องใช้เป็นหลักฐาน

**ค่าตั้งต้นถูกคงไว้โดยตั้งใจ** ไม่ปรับตามตัวเลข sanity check เพราะจะเป็นการ
เดาบนข้อมูลผิดชุด รอปรับเทียบด้วยภาพจริง

### ต้องการอะไรถึงจะปรับเทียบได้

| | จำนวน | เหตุผล |
|---|---|---|
| คน | อย่างน้อย 3 คน | ไม่มีคนที่สอง = วัด FAR ไม่ได้ |
| ภาพต่อคน | อย่างน้อย 3 ภาพ | ไม่มีภาพที่สอง = วัด FRR ไม่ได้ |

สำคัญกว่าจำนวนคือ **ต้องถ่ายด้วยเว็บแคมและแสงแบบเดียวกับตอนใช้งานจริง**
ทางที่ดีที่สุดคือให้แต่ละคนมี 1 ภาพลงทะเบียน (ถ่ายดี) และที่เหลือเป็นภาพเว็บแคม
สภาพปกติ เพราะนั่นคือสิ่งที่ระบบต้องเทียบกันจริงๆ

วางที่ `face-service/tests/faces/` แล้ว:

```bash
sh calibrate.sh
```
