# ผู้ช่วย AI — และเส้นที่ห้ามข้าม

AI ในระบบนี้มีหน้าที่เดียว: **ช่วยคนอ่าน** ไม่ใช่ช่วยคนตัดสิน

---

## ทำไมถึงต้องมี

ผู้ตรวจที่มีบันทึกการเรียน 100 ครั้งอ่านไม่ไหว สุดท้ายจึงไม่อ่านเลย
และครั้งที่สำคัญจริงก็หลุดไป — สรุปสั้นๆ ที่ชี้ว่าครั้งไหนผิดปกติ คือสิ่งที่ทำให้กองนี้ตรวจได้จริง

อีกงานหนึ่งคือชี้ข้อสอบที่นำเข้าจาก PDF แล้วข้อความไทยเพี้ยน คนอ่านภาษาไทยเห็นปุ๊บรู้ทันที
แต่ regular expression ไม่มีวันจับได้ — ตรงกับข้อจำกัดที่บันทึกไว้ใน [PDF import](../README.md)

---

## เส้นที่ห้ามข้าม

บังคับไว้ในโค้ด ไม่ใช่ฝากไว้กับวินัยของผู้เรียก เพราะพลาดแล้วคือเหตุการณ์ละเมิดข้อมูล ไม่ใช่บั๊ก

### 1. ไม่มีข้อมูลชีวมิติออกไป

โมเดล **ไม่เห็น**: ภาพนิ่ง คลิป ค่า embedding คะแนน similarity คะแนน liveness ชื่อไฟล์ หรือ userid

โมเดล **เห็นเฉพาะ**: จำนวนผลตรวจแยกตามผลตัดสิน (`identity:pass` 3 ครั้ง) ชื่อเหตุการณ์และจำนวนครั้ง
ระยะเวลา สถานะการจบ และ snapshot ของนโยบาย — ซึ่งทั้งหมดพิมพ์อยู่บนหน้ารายงานอยู่แล้ว

payload สร้างจาก **whitelist** ไม่ใช่การตัดฟิลด์ออก — ถ้าเพิ่มคอลัมน์ใหม่ในตารางวันหลัง
มันจะไม่ไหลออกไปเองโดยไม่มีใครตัดสินใจ มีเทสต์ตรวจ payload จริงว่าไม่มีคำต้องห้ามหลุด

> เอกสารความยินยอมบอกผู้เรียนว่าข้อมูลใบหน้าไปที่บริการที่ไม่เก็บอะไรไว้
> การส่งไปโมเดลภาษาแทนจะทำให้ประโยคนั้นเป็นเท็จ

### 2. AI ไม่ตัดสินอะไร

คำสั่งที่ให้โมเดลระบุชัด และมีเทสต์อ่าน prompt เพื่อกันไม่ให้ใครลบทิ้งเงียบๆ:

- ห้ามบอกหรือบอกเป็นนัยว่าผู้เรียนทุจริต หรือไม่ทุจริต
- ห้ามแนะนำให้ผ่าน ไม่ผ่าน หรือลงโทษใคร
- ถ้าบันทึกไม่มีอะไรผิดปกติ ให้บอกตรงๆ ไม่ใช่หาเรื่องมาเติม
- ถ้าข้อมูลน้อยเกินจะสรุป ให้บอกว่าน้อยเกินไป

ผลลัพธ์ถูกแสดงเป็น **"ร่างสรุป"** พร้อมข้อความกำกับว่าไม่ใช่ข้อสรุป โมเดลไม่ได้เห็นภาพ
และไม่มีส่วนตัดสิน — การตัดสินยังอยู่กับกติกาและกับคน

### 3. ปิดไว้เป็นค่าเริ่มต้น

ไม่มีส่วนไหนของระบบพึ่งพา AI ปิดอยู่แล้วทุกอย่างทำงานครบเหมือนเดิม
และถ้า gateway ล่ม หน้าจอจะบอกว่าล่ม ไม่ใช่เงียบแล้วปล่อยให้ผู้ตรวจคิดว่าไม่มีอะไรจะสรุป

```
                                       · ตรวจคำตอบก่อนส่งออก
```

ดูสัญญาการเชื่อมต่อเต็มที่ [AI-CONTRACT.md](AI-CONTRACT.md)

### ทำไมต้องแยกเป็นบริการ

ตอนที่ prompt และกฎเรื่อง payload อยู่ในปลั๊กอิน มันทำงานได้ดีตราบใดที่เราถือทั้งสองฝั่ง
แต่ดีลนี้ลูกค้าเอาซอร์สไปดูแลเอง — กฎก็กลายเป็นของเขาที่แก้ได้ payload ก็ของเขาที่ขยายได้
ในขณะที่สรุปที่ออกมายังมีชื่อเราติดอยู่ และเรายังต้องรับสายเวลามันพัง

พอย้ายมาเป็นบริการ ประโยคเดิมเปลี่ยนความหมายไปเลย:

| | ก่อน | หลัง |
|---|---|---|
| "ไม่มีข้อมูลชีวมิติออกไป" | วินัยของผู้เรียก | โค้ดใน `contract.py` |
| ผู้เรียกส่งผิด | รั่วเงียบๆ | `422` พร้อมชื่อฟิลด์ |
| ลูกค้าแก้ schema ตัวเอง | AI พัง เราโดนโทษ | ไม่กระทบ |
| ใครลบ guardrail ได้ | ใครก็ได้ที่แก้ปลั๊กอิน | เราเท่านั้น |

**ขอบเขตความรับผิดชอบชัด** — เราดูแลบริการ ลูกค้าดูแล LMS ซึ่งเป็นรูปแบบเดียว
ที่สัญญาดูแลรายเดือนมีความหมาย

### กฎที่บังคับด้วยรูปทรงของข้อมูล

`checks` `events` `evidence` รับเฉพาะ**จำนวนเต็ม** — และคะแนน similarity, liveness,
confidence **เป็นทศนิยมทั้งหมด** ฉะนั้น payload ปฏิเสธค่าเหล่านั้นเองโดยไม่ต้องเดาชื่อฟิลด์

เป็นกฎเดียวที่ทนต่อการเปลี่ยนชื่อฟิลด์เพื่อเลี่ยงตัวกรองคำ

### ตรวจคำตอบ ไม่ใช่แค่ตรวจคำถาม

**วัดจริงกับ qwen2.5:7b: คำสั่งห้ามตัดสินใน prompt เอาอยู่แค่ 1 ใน 5 ครั้ง**
โมเดลเขียนประโยคทำนอง *"ยังไม่มีหลักฐานชัดเจนว่าเกิดจากการกระทำผิด"* ซ้ำๆ
ซึ่งคือคำพิพากษาที่เขียนในรูปการปฏิเสธ และผู้ตรวจก็อ่านมันแบบนั้น

คำสั่งที่โมเดล "ทำตามเกือบทุกครั้ง" ไม่ใช่การรับประกัน จึงย้ายไปบังคับที่ `guard.py`
ซึ่งอ่านข้อความที่กลับมาจริง ถ้าเจอคำพิพากษาจะถามใหม่หนึ่งครั้ง ยังเจออยู่ก็ตอบ
`guardrail_violation` แทน — **ผู้ตรวจไม่มีวันได้เห็นสรุปที่ตัดสิน**

การล้มเหลวดังๆ คือพฤติกรรมที่ตั้งใจ ถ้าโมเดลที่เลือกเขียนสรุปโดยไม่ตัดสินไม่ได้
ผู้ดูแลต้องรู้ว่าโมเดลนั้นไม่เหมาะกับงานนี้ ไม่ใช่ได้อ่านคำตัดสิน

### LiteLLM

[LiteLLM](https://github.com/BerriAI/litellm) (MIT) ยังอยู่ใน profile `ai` สำหรับกรณี
ที่ต้องต่อผู้ให้บริการหลายเจ้าหรือทำ budget/rate limit แต่**ไม่จำเป็นแล้ว** —
บริการพูด OpenAI-compatible ตรงๆ จึงต่อ Ollama ได้โดยไม่ต้องมีอะไรคั่นกลาง

### ทำไมไม่ใช้ agent framework

LangGraph, CrewAI, AutoGen เหมาะกับงานที่ agent ต้องเรียกเครื่องมือหลายขั้นและตัดสินใจเอง
งานที่นี่คือ "สรุปตัวเลขชุดนี้" และ "ข้อความนี้เพี้ยนไหม" — เรียก chat completion ครั้งเดียวจบ

การใส่ framework เข้ามาตอนนี้คือเพิ่มน้ำหนักโดยไม่ได้อะไร ถ้าวันหนึ่งมีงานที่ต้องเรียกเครื่องมือ
หลายขั้นจริง ค่อยพิจารณาใหม่

## หน้าเปิด/ปิดสำหรับผู้ดูแล

`/local/kaiproctor/ai.php` — Site administration → Plugins → Local plugins → ผู้ช่วย AI

สวิตช์อยู่ข้างข้อมูลที่ใช้ตัดสินว่า**เปิดได้หรือเปล่า** ไม่ใช่สวิตช์เปล่าๆ:

- โมเดลไหนตอบงานไหน (สรุป / นำทาง / ตรวจข้อสอบ)
- ปลายทางอยู่ที่ไหน และ **เป็นเครื่องที่คุณควบคุมเองหรือของคนอื่น**
- บริการติดต่อได้ไหม เวอร์ชันสัญญาเท่าไร

ที่ต้องมีเพราะคำถามที่ตัดสินว่าเปิดได้ไหมตามสัญญาข้อมูลของลูกค้า — ข้อความไปที่ไหน
เครื่องใครเป็นคนตอบ — เป็นข้อเท็จจริงของ*บริการ* ไม่ใช่ของ*การตั้งค่า* สวิตช์ที่ไม่มี
ข้อมูลพวกนี้อยู่ข้างๆ คือการขอให้คนตัดสินโดยไม่เห็นอะไรเลย

ปลายทางอยู่นอกเครือข่าย → เตือนสีเหลืองพร้อมบอกว่าอะไรถูกส่งออกไปบ้าง
เปิดอยู่แต่โมเดลตอบไม่ได้ → เตือนสีแดง สถานะนี้เงียบไม่ได้ เพราะทุกครั้งที่มีคนใช้จะล้มเหลว

อ่านสถานะบริการได้**โดยไม่ต้องเปิดใช้งานก่อน** ไม่งั้นคนที่แค่อยากดูจะต้องเปิดบนไซต์จริง
สักพักแล้วค่อยปิด

การสลับสวิตช์ต้องเป็น POST พร้อม sesskey — การตัดสินว่าข้อมูลกิจกรรมผู้เรียนออกนอก
องค์กรหรือไม่ ไม่ควรทำได้ด้วยลิงก์ที่มีคนส่งมาให้กด

## เปิดใช้งาน

บริการขึ้นมาพร้อม stack ปกติ ไม่ต้องใช้ profile:

```bash
docker compose up -d ai-service
```

ค่าเริ่มต้นชี้ไปที่ **Ollama บนเครื่องที่รัน Docker** ด้วยโมเดล `qwen2.5:7b-instruct`
เปลี่ยนได้ที่ `.env`:

```
AI_LLM_BASE_URL=http://host.docker.internal:11434/v1
AI_LLM_MODEL=qwen2.5:7b-instruct
```

ฝั่ง Moodle เปิดที่ Site administration → Plugins → Local plugins →
KAISER Proctor → ผู้ช่วย AI (ปิดเป็นค่าเริ่มต้น)

**ก่อนชี้ไปที่โมเดลบนคลาวด์** ต้องตรวจว่าการส่งข้อมูลกิจกรรมผู้เรียนออกนอกองค์กร
อยู่ในขอบเขตของเอกสารความยินยอมและสัญญาประมวลผลข้อมูลแล้ว ถ้ายังไม่ครอบคลุม
ให้ใช้โมเดลบนเครื่องต่อไป ซึ่งเป็นค่าเริ่มต้นอยู่แล้ว

## ผู้ช่วยนำทาง

งานที่สาม: ผู้เรียนถามว่าอะไรอยู่ตรงไหน แล้วได้ลิงก์จริงกลับไป

```
ผู้เรียนถาม ──> Moodle ค้นจากสิ่งที่ "คนนี้" เปิดได้ ──> ไม่เจอ: ตอบไปเลย ไม่เรียกโมเดล
                                                    └──> เจอ: POST /ask พร้อมรายการหน้า
```

### ค้นที่ Moodle ไม่ใช่ที่บริการ

การลงทะเบียน กลุ่ม เงื่อนไขวันเวลา และการซ่อนกิจกรรม เป็นตัวตัดสินว่าหน้านั้น
"มีอยู่" สำหรับคนนี้หรือเปล่า — และไม่มีอะไรในนั้นรอดจากการ export ออกไปที่อื่น

**คอร์สของคนอื่นไม่เคยเข้ามาในดัชนีเลย** ไม่ใช่เข้ามาแล้วถูกกรองออก เพราะการตอบว่า
"คุณไม่ได้ลงทะเบียนคอร์ส X" ก็คือการบอกว่าคอร์ส X มีอยู่ ระบบที่ไม่เคยเห็นมัน
ปฏิเสธไม่ได้แม้จะอยากปฏิเสธ

### ไม่เจอ = ไม่เรียกโมเดล

โมเดลที่ได้รับคำถามโดยไม่มีเนื้อหาประกอบ **จะตอบอยู่ดี** จากสิ่งที่มันเรียนมาจากที่อื่น
และคำตอบที่ฟังดูมั่นใจเกี่ยวกับหน้าที่ไม่มีอยู่จริงบนเว็บนี้ คือความล้มเหลวที่ต้องกัน

ตัดสินในโค้ดถูกกว่าและแน่นอนกว่าการเขียน prompt ขอให้โมเดลปฏิเสธเอง —
เป็นหลักการเดียวกับ `guard.py` และเป็นเหตุผลเดียวกัน

### ลิงก์ที่แต่งเองถูกทิ้ง

ความล้มเหลวที่แพงที่สุดของฟีเจอร์นี้ไม่ใช่ประโยคที่เขียนไม่สวย แต่คือลิงก์ที่ดูถูกต้อง
แล้วกดไปเจอ 404 ผู้เรียนกดครั้งเดียวแล้วเลิกเชื่อคำตอบถัดไปทั้งหมด

บริการเทียบทุกลิงก์ในคำตอบกับรายการที่ส่งไป ไม่ตรง = ถามใหม่ ยังไม่ตรง = `invented_link`

### ทำไมใช้ trigram ไม่ใช่ตัดคำ

ภาษาไทยไม่มีช่องว่าง การตัดคำต้องมีพจนานุกรม และเวลาผิดมัน**เงียบ** — คือหาไม่เจอ
เฉยๆ โดยไม่มี error ให้ใครเห็น trigram ไม่ต้องใช้พจนานุกรม และคำที่พิมพ์ไม่ครบ
ยังทับกับชื่อหน้าที่มันอยู่ได้

### ตอบเรื่องข้อสอบและคะแนนได้

หน้าที่เป็นข้อสอบจะแนบ**ผลของผู้ถามเอง**ไปด้วย: คะแนน คะแนนเต็ม ร้อยละ เกณฑ์ผ่าน
ผ่าน/ไม่ผ่าน จำนวนครั้งที่สอบ วันเปิด-ปิด เวลาทำ

อ่านจาก**สมุดคะแนน** ไม่ใช่จากตารางการสอบ เพราะสมุดคะแนนคือสิ่งที่ผู้เรียนเห็นในหน้าอื่น
ของเว็บ — ผู้ช่วยที่พูดไม่ตรงกับหน้ารายงานคะแนน แย่กว่าผู้ช่วยที่ไม่พูดเลย

และดึงสดตอนตอบ **ไม่ได้เก็บไว้ในดัชนีที่แคช** คนที่เพิ่งส่งข้อสอบเสร็จต้องไม่ถูกบอก
คะแนนของสัปดาห์ที่แล้ว

#### เส้นสามเส้นที่ยังอยู่ครบ

**หนึ่ง — ของตัวเองเท่านั้น** contract ไม่มีคีย์สำหรับผู้เรียนคนอื่น ไม่มีค่าเฉลี่ยห้อง
ไม่มีชื่อคน โมเดลเปิดเผยสิ่งที่ไม่เคยได้รับไม่ได้ ต่อให้ถูกถามตรงๆ ก็ตาม

**สอง — โมเดลห้ามคิดเลข** ทุกตัวเลขรวมถึงร้อยละถูกคำนวณใน PHP แล้วส่งไปเป็นค่าสำเร็จ
บริการเก็บตัวเลขทุกตัวในคำตอบมาเทียบกับที่ส่งไป ไม่ตรงคือทิ้งคำตอบ (`unsupported_number`)

ทดสอบจริง: ได้ 8 จาก 10 แล้วถามว่า "ขาดอีกกี่คะแนนถึงจะเต็ม" — โมเดลตอบ "2 คะแนน"
และถูกบล็อก เพราะ 2 ไม่เคยถูกส่งไป

> เวอร์ชันแรกของกฎนี้**ไม่ทำงาน** ผมเทียบกับ prompt ทั้งก้อน ซึ่งมีเลขลำดับรายการ
> (1. 2. 3.) และ id ใน URL ปนอยู่ เลข 2 จึงนับว่า "ส่งมาแล้ว" — เจอตอนทดสอบจริง
> ตอนนี้เทียบกับ `facts` เท่านั้น และตัดลิงก์ออกจากคำตอบก่อนตรวจ

**สาม — รายงาน ไม่ใช่ตัดสิน** โมเดลบอกได้ว่าผ่านหรือไม่ผ่าน เพราะ**เกณฑ์ผ่านเป็นกฎที่
ครูตั้งและสมุดคะแนนตัดสินไปแล้ว** การพูดซ้ำคือการรายงาน ไม่ใช่การตัดสิน — คนละเรื่องกับ
ผู้ช่วยผู้ตรวจที่ห้ามตัดสินเรื่องทุจริตโดยเด็ดขาด และกฎข้อนั้นไม่ถูกแตะเลย

prompt ยังห้ามวิจารณ์ว่าคะแนนดีหรือแย่ ห้ามทำนายคะแนนครั้งหน้า และห้ามแนะนำว่าควร
สอบใหม่ไหม — นั่นเป็นเรื่องของผู้เรียนกับครู

#### ผลกระทบต่อ PDPA

**สิ่งที่ออกจากไซต์เปลี่ยนไปแล้ว** เดิมมีแต่ชื่อเหตุการณ์และจำนวนครั้ง ตอนนี้มีคะแนน
ของผู้เรียนที่ถามด้วย ยังไม่ใช่ข้อมูลชีวมิติ แต่เป็นข้อมูลส่วนบุคคล

ค่าเริ่มต้นชี้ไปที่โมเดลบนเครื่องตัวเอง จึงไม่ออกไปไหน ถ้าจะชี้ไปคลาวด์ **หน้าคอนโซล
ขึ้นเตือนสีเหลืองพร้อมข้อความที่แก้ให้ตรงกับความจริงใหม่แล้ว** และข้อความบนหน้าผู้ช่วย
ที่เคยเขียนว่า "มองไม่เห็นคะแนนของคุณ" ถูกแก้ทันทีที่ฟีเจอร์นี้เข้า — ประโยคที่กลายเป็นเท็จ
บนหน้าที่ผู้ใช้อ่าน แย่กว่าการไม่เขียนอะไรเลย

### MIN_SCORE = 0.10 มาจากการวัด

กวาดค่า 0.01–0.40 กับชุดคำถามที่ติดป้ายไว้ 25 ข้อที่ควรเจอ + 12 ข้อที่ไม่ควรเจออะไรเลย
(`tests/support/ask-questions.json`) ผลเต็มที่ [reports/ASK-CALIBRATION.txt](../reports/ASK-CALIBRATION.txt)

| threshold | recall | top-1 | ตอบคำถามนอกเรื่อง |
|---|---|---|---|
| 0.01 | 100% | 92% | **58%** |
| 0.07–0.08 | 96% | 92% | **8%** |
| **0.10** | **96%** | **92%** | **0%** ← เลือก |
| 0.11–0.14 | 92% | 88% | 0% |
| 0.20+ | 80% | 80% | 0% |

วัดใหม่ตอนเพิ่มเรื่องคะแนน เพราะคำถามเรื่องผลสอบมักไม่มีชื่อหน้าอยู่ในนั้นเลย
("ยังสอบได้อีกกี่ครั้ง") จึงต้องเพิ่มคำว่า คะแนน/ผลสอบ/ผ่าน/เกณฑ์/ครั้ง เข้าไปในคำพ้อง
ของข้อสอบ และค่าที่เลือกได้ขยับจาก 0.14 เป็น 0.10

**การไม่ตอบคำถามนอกเรื่องถือเป็นข้อบังคับ ไม่ใช่ด้านหนึ่งของการแลกเปลี่ยน** เพราะ
"คำถามที่ไม่มีหน้าตรงกันจะไม่ไปถึงโมเดล" เป็นคำสัญญาที่ฟีเจอร์นี้ประกาศไว้ ค่าที่ปล่อยผ่าน
1 ใน 10 ไม่ได้ทำตามคำสัญญานั้น แค่ใกล้เคียง — ซึ่งเป็นคนละผลิตภัณฑ์ ส่วนการหาไม่เจอ
เป็นปัญหาคุณภาพที่ผู้เรียนแก้เองได้ด้วยการระบุชื่อหน้า

ในบรรดาค่าที่ไม่ปล่อยอะไรผ่านเลย เลือกตัวที่ recall ดีที่สุด และถ้าเสมอกันเลือก**ตัวสูงสุด**
เพื่อให้อยู่กลางที่ราบ ไม่ใช่ริมขอบ — คำถามที่พิมพ์ต่างไปนิดหน่อยจะได้ไม่พลิกผล

### การวัดเจอปัญหาจริงหนึ่งอย่าง

"ขอลิงก์หน้าคอร์สหน่อย" หาไม่เจอเลย เพราะคอร์สชื่อ "หลักสูตร..." และคนที่พูดว่า "คอร์ส"
ไม่มีตัวอักษรตรงกันสักตัว — **คนเรียกชื่อประเภทของสิ่งนั้นเมื่อจำชื่อจริงไม่ได้ ซึ่งคือตอนที่
ต้องการผู้ช่วยพอดี** จึงเพิ่มคำพ้องตามประเภท (คอร์ส/หลักสูตร/วิชา, ข้อสอบ/แบบทดสอบ/สอบ)
เข้าไปในการให้คะแนน ไม่ได้ส่งให้โมเดล — contract จะปฏิเสธฟิลด์นี้อยู่แล้ว

recall ที่ค่าต่ำขยับจาก 94.7% เป็น 100% และค่าที่เลือกได้ขยับจาก 0.08 (เดา) เป็นค่าที่วัดได้

**ข้อจำกัด:** วัดกับเว็บสาธิตด้วยคำถามที่ผมเขียนเอง — 25 ข้อแยกความละเอียดได้ไม่ดีกว่า
ประมาณ 4 จุดเปอร์เซ็นต์ ต้องวัดใหม่ด้วยคำถามที่ผู้เรียนจริงพิมพ์ บนเว็บที่มีชื่อคอร์สจริง
เทสต์ `test_the_shipped_threshold_still_earns_its_number` จะพังถ้ามีใครแก้การให้คะแนน
แล้วทำให้ตัวเลขนี้ไม่จริงอีกต่อไป

### ลด context ลงช่วยได้ และไม่เสียความแม่นยำ

### สองโมเดลต้องการ VRAM พอที่จะอยู่พร้อมกัน

ราคาที่ต้องจ่ายของการแยกโมเดล และเป็นข้อที่ผมมองข้ามไปตอนตัดสินใจ

วัดบนเครื่องนี้ (RTX 3050 6 GB): `qwen3:8b` กินหน่วยความจำ **7.8 GB** แต่ลง VRAM ได้แค่
4.2 GB ที่เหลือล้นไปที่ CPU และเมื่อสลับไปงานสรุปที่ใช้ `qwen2.5:7b` (4.7 GB)
qwen3 ถูกเตะออกทั้งตัว แล้วโหลดกลับใหม่ในคำขอถัดไป — **ครั้งละประมาณ 35 วินาที**

ผลที่เห็น: ชุดเทสต์เต็มยืดจาก 28 นาทีเป็น 65 นาที และเทสต์ที่พึ่งโมเดลเป็นตัวแรกที่ล้ม
เพราะไปชนเพดาน 300 วินาที

**ถ้าจะใช้สองโมเดลจริง ต้องมี VRAM พอให้ทั้งคู่อยู่พร้อมกัน** ประมาณ 12 GB ขึ้นไป
ไม่งั้นทุกคำขอที่สลับงานจ่ายค่าโหลดใหม่ ทางเลือกอื่นคือใช้โมเดลเดียวทั้งหมด
(แลกกับความแม่นยำที่วัดไว้ด้านล่าง) หรือชี้ไปที่โมเดลบนคลาวด์ซึ่งไม่มีปัญหานี้เลย
