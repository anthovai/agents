# ติดตั้งบนเซิร์ฟเวอร์

สำหรับคนที่ต้องเอาระบบนี้ขึ้นเครื่องจริง ไม่ใช่แล็ปท็อป

---

## ⚠️ อ่านก่อน: สองข้อที่ยังไม่พร้อมสำหรับการใช้งานจริง

**1. เกณฑ์เทียบใบหน้ายังไม่ได้ปรับเทียบ** `FACE_MATCH_THRESHOLD=0.363` เป็นค่าอ้างอิงของ
ผู้พัฒนา SFace ไม่ใช่ค่าที่วัดกับกล้องของผู้เรียนคุณ ระบบจะทำงาน จะบันทึกผล และจะตัดสิน
ด้วยตัวเลขที่ไม่มีใครเคยตรวจสอบ

ก่อนใช้ตัดสินอะไรที่มีผลกับคน ต้องเก็บภาพจากเว็บแคมจริงอย่างน้อย 3 คน คนละ 3 ภาพ
ใส่ใน `face-service/tests/faces/` แล้วรัน `sh calibrate.sh` — ดู [FACE-VALIDATION.md](FACE-VALIDATION.md)

**2. ยังไม่เคยทดสอบกับผู้ใช้จำนวนมากจริง** วัดเฉพาะ face-service ตัวเดียวบนแล็ปท็อป
(`reports/FACE-LOAD.txt`) ไม่ได้วัดทั้งระบบพร้อมผู้ใช้จริง ดูหัวข้อ "ขนาดเครื่อง" ด้านล่าง

ทั้งสองข้อไม่ได้ขวางการติดตั้งเพื่อทดลองใช้ แต่ขวางการนำไปออกใบรับรอง

---

## สิ่งที่ต้องมี

| | ขั้นต่ำ | หมายเหตุ |
|---|---|---|
| CPU | 4 คอร์ | face-service กิน CPU ล้วน ไม่ใช้ GPU |
| RAM | 8 GB | +12 GB ถ้าจะรันโมเดล AI บนเครื่องเดียวกัน |
| ดิสก์ | 40 GB | หลักฐานคือตัวกินพื้นที่ ดู "หลักฐานโตเร็วแค่ไหน" |
| OS | Linux ที่มี Docker Engine 24+ | |
| โดเมน + ใบรับรอง TLS | จำเป็น | กล้องในเบราว์เซอร์ทำงานเฉพาะบน HTTPS |

**ไม่มี HTTPS = ไม่มีกล้อง** เบราว์เซอร์บล็อก `getUserMedia` บนหน้าที่ไม่ใช่ HTTPS
(ยกเว้น localhost) ทั้งการลงทะเบียนใบหน้าและการเฝ้าดูจะใช้ไม่ได้เลย ไม่ใช่เรื่องความปลอดภัย
เชิงนโยบาย แต่เป็นข้อจำกัดที่เบราว์เซอร์บังคับ

## ติดตั้ง

```bash
git clone <repo> kai-proctor && cd kai-proctor
```

```bash
sh face-service/models/fetch.sh
```

```bash
cp deploy/.env.example deploy/.env
```

แก้ `deploy/.env` ให้ครบ — compose จะไม่ยอมสตาร์ทถ้าค่าสำคัญยังว่าง ซึ่งตั้งใจให้เป็นแบบนั้น
ดีกว่าเดาค่าให้แล้วขึ้นระบบด้วยรหัสผ่านที่เดาได้

```bash
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env up -d --build
```

ครั้งแรกใช้เวลาสักพัก — ติดตั้ง Moodle และภาษาไทยอัตโนมัติ ดูความคืบหน้าด้วย

```bash
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env logs -f moodle
```

### ตั้งค่าที่ต้องทำด้วยมือหลังติดตั้ง

1. **เปลี่ยนรหัสผ่านผู้ดูแล** ที่ตั้งไว้ใน `.env` ยังอยู่ในไฟล์บนเครื่องตราบที่ยังไม่ลบ
2. **ตั้งนโยบายความยินยอม PDPA** — Site administration → Privacy → Policy settings
   ตัวอย่างข้อความอยู่ใน `docker/seed-demo.php` (อย่าใช้ตรงๆ ให้ฝ่ายกฎหมายตรวจก่อน)
3. **ตรวจหน้าสถิติ** `/local/kaiproctor/stats.php` ว่า face service ต่อได้และโหลดโมเดล
   liveness แล้ว

## TLS และ reverse proxy

Moodle เปิดพอร์ตไว้ที่ `127.0.0.1:8080` เท่านั้น ไม่ได้เปิดออกอินเทอร์เน็ต
ให้ proxy บนเครื่องเดียวกันรับ HTTPS แล้วส่งต่อ

Caddy สั้นที่สุดและออกใบรับรองให้เอง:

```
proctor.example.co.th {
    reverse_proxy 127.0.0.1:8080
    request_body {
        max_size 512MB
    }
}
```

nginx:

```nginx
server {
    listen 443 ssl http2;
    server_name proctor.example.co.th;

    # คลิปหลักฐานอัปโหลดจากเบราว์เซอร์ และไฟล์วิดีโอบทเรียนที่ผู้สอนอัปโหลดเข้ามา
    # ค่าเริ่มต้น 1M เล็กเกินไปมาก ต้องไม่น้อยกว่า upload_max_filesize ใน PHP
    # มิฉะนั้นการอัปโหลดจะถูกตัดที่ proxy โดยที่ Moodle ไม่มีโอกาสอธิบายอะไรเลย
    client_max_body_size 512M;

    # ผู้ช่วย AI บนโมเดลที่รันเองใช้เวลาได้ถึง 300 วินาที
    # ลำดับ timeout ต้องกว้างออกด้านนอกเสมอ:
    #   ai-service 300 < ai_client 330 < Apache 420 < ตัวนี้
    proxy_read_timeout 450s;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

`MOODLE_SSLPROXY=1` ใน `.env` เป็นตัวบอก Moodle ว่ามี proxy อยู่ข้างหน้า **ถ้าลืม**
Moodle จะสร้างทุกลิงก์เป็น `http://` แล้วเบราว์เซอร์บล็อกทรัพยากรของหน้าตัวเองเป็น mixed
content — อาการคือเว็บโหลดครึ่งๆ และดูเหมือนพังด้วยเหตุที่ไม่เกี่ยวกับ proxy เลย

## ขนาดเครื่อง

วัดจริงแล้ว แต่วัดแค่ face-service และวัดบนแล็ปท็อป — `reports/FACE-LOAD.txt`

| | รับได้ประมาณ |
|---|---|
| ดูบทเรียนที่มีการเฝ้าดูพร้อมกัน | ~600 คน (คนละ 1 คำขอ ต่อ 120 วินาที) |
| **ลงทะเบียนใบหน้าพร้อมกัน** | **~1–2 คน ต่อ 4 คอร์** |

**การลงทะเบียนคือคอขวด ไม่ใช่การเฝ้าดู** เพราะ liveness challenge ยิงคำขอวินาทีละหลายครั้ง
**ต่อคน** ตลอดเวลาที่หันหน้า — คน 100 คนที่เริ่มสอบพร้อมกันคือคน 100 คนที่ลงทะเบียนพร้อมกัน

ผลที่ตามมาในทางปฏิบัติ: **ให้ผู้เรียนลงทะเบียนใบหน้าล่วงหน้า ไม่ใช่ตอนเปิดห้องสอบ**
ถ้าเลี่ยงไม่ได้ ต้องเพิ่ม CPU ตามจำนวนคนที่จะลงทะเบียนพร้อมกัน หรือรัน face-service
หลายชุดหลัง load balancer (บริการไม่เก็บสถานะ จึงขยายแนวนอนได้)

## หลักฐานโตเร็วแค่ไหน

ประมาณจากค่าเริ่มต้น: คลิปสุ่ม 4 ครั้ง/ชั่วโมง ยาว 8 วินาที + ภาพนิ่งตอนเกิดเหตุ

- ผู้เรียน 1 คน เรียน 1 ชั่วโมง ≈ **2–5 MB**
- 100 คน × 20 ชั่วโมง ≈ **4–10 GB**
- เก็บ 180 วันตามค่าเริ่มต้น `retentiondays`

**ถ้า cron ไม่ทำงาน ไม่มีอะไรถูกลบเลย** และดิสก์จะเต็มเงียบๆ หน้าสถิติเตือนเรื่องนี้ไว้
ให้ดูเป็นประจำ — ดู [ADMIN.md](ADMIN.md)

## สำรองข้อมูล

```bash
sh deploy/backup.sh /var/backups/kaiproctor
```

เอาสองอย่างที่สร้างใหม่ไม่ได้: ฐานข้อมูล (ใครทำอะไร) และ moodledata (ไฟล์หลักฐานที่แถวเหล่านั้นชี้ถึง)
**ขาดอย่างใดอย่างหนึ่งคือกู้คืนมาแล้วระบบบอกว่ามีภาพหลักฐาน แต่เปิดไม่ได้**

สคริปต์ตรวจสิ่งที่เขียนออกมาให้ด้วย — ทั้งสองไฟล์ต้องคลายได้ และ archive ต้องมีไฟล์
ใน `filedir` จริง ถ้าไม่ผ่านจะ exit ไม่ใช่เขียนไฟล์เปล่าไว้ให้

> เวอร์ชันแรกของสคริปต์นี้ต่อท่อ binary ผ่านเชลล์ ผลคือได้ไฟล์ขนาด 945,459 ไบต์
> ที่ `tar -t` อ่านแล้วไม่มีอะไรอยู่ข้างในเลย — ดูเหมือน backup ขนาดถูกต้อง และว่างเปล่า
> ตอนนี้สร้าง archive ในคอนเทนเนอร์แล้ว copy ออกมา

ตั้ง cron ของเครื่อง:

```
15 3 * * *  cd /srv/kai-proctor && sh deploy/backup.sh /var/backups/kaiproctor
```

**และเอาไฟล์ออกนอกเครื่อง** backup ที่อยู่บนดิสก์เดียวกับสิ่งที่มันสำรองไม่ใช่ backup

### กู้คืน

```bash
sh deploy/restore.sh /var/backups/kaiproctor/20260812-031500
```

ทำลายของเดิม โดยตั้งใจ — ต้องพิมพ์ชื่อฐานข้อมูลยืนยันก่อน

**ซ้อมกู้คืนบนเครื่องสำรองก่อนถึงวันที่ต้องใช้จริง** สิ่งที่ต้องตรวจหลังกู้คืนคือ
**เปิดหน้ารายงานแล้วภาพหลักฐานขึ้นจริงไหม** — นั่นคือจุดเดียวที่การกู้คืนเฉพาะฐานข้อมูล
จะผิด และไม่มีอะไรอื่นฟ้อง

## อัปเกรด

```bash
git pull
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env up -d --build
```

ปลั๊กอินถูก build เข้า image ไม่ได้ mount จาก working copy — **image tag คือสิ่งที่ระบุว่า
กำลังรันอะไรอยู่** ต่างจากชุด dev ที่แก้ไฟล์แล้วมีผลทันที ซึ่งบนเซิร์ฟเวอร์เป็นสิ่งที่ไม่ควรมี

entrypoint รัน upgrade ให้เองเมื่อฐานข้อมูลมีอยู่แล้ว **สำรองข้อมูลก่อนอัปเกรดเสมอ**
การ upgrade ของ Moodle ย้อนกลับไม่ได้

## ที่ยังไม่มีในเอกสารนี้ เพราะยังไม่ได้ทำ

พูดให้ชัดเพื่อไม่ให้ใครวางแผนบนสิ่งที่ไม่มี:

| | สถานะ |
|---|---|
| High availability / หลาย instance | ❌ ออกแบบไว้ให้ขยาย face-service ได้ แต่ยังไม่เคยทำจริง |
| ย้ายไฟล์ไป object storage (S3) | ❌ หลักฐานอยู่บนดิสก์ของเครื่อง |
| Monitoring / alert อัตโนมัติ | ❌ มีหน้าสถิติให้คนเปิดดู ไม่มีการแจ้งเตือน |
| Log rotation ของ container | ❌ ตั้ง `max-size` ใน daemon.json ของ Docker เอง |
| ทดสอบกู้คืนอัตโนมัติ | ❌ ต้องซ้อมด้วยมือ |
